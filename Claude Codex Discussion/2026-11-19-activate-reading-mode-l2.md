### 發現

#### R1｜排隊期間切到編輯模式，可以繞過未存文字檢查

**軸：規格。證據：已在記憶體探針重現，Obsidian 對未存文字的處理待驗證。**

- **觸發、預期與實際**：按下確認時同篇只開在閱讀模式。狀態操作排在另一筆寫入後面，等待期間把同篇切到編輯模式並輸入一行，然後放行佇列。依暫停／恢復的驗收，此時應提示有未存修改並停止變更狀態。實際上，待審版回 `null`，直接把檔案寫成「啟用」並記一行 `set: status`，替身的編輯器仍是「草稿」加新輸入的一行。基準版在同一探針走編輯器，狀態與新輸入的一行一起存入。待審版選好寫入路徑後就帶著 `null` 排隊，`fillFile()` 寫入時只檢查檔案內容。 `src/obsidian/deck-status.ts:46` · `src/state/index.ts:917` · `src/state/writes.ts:348` · `tasks/quiz-practice.md:101`
- **真實路徑與影響**：電腦版的共用寫入佇列允許這個時序。估計低頻，需要前一筆寫入拖長等待，或在另一個視窗操作，且同篇在落盤前已出現未存文字。已確認的是受阻保護被繞過。Windows Obsidian 1.15.1 如何合併或重讀、文字是否被覆蓋、後續自動存檔是否把狀態寫回草稿，均待驗證。
- **建議處理**：重新凍結前，以暫存卡組在寫入佇列加一道可控等待，核對操作提示、磁碟全文、編輯器全文和 `set: status`。若實機可走到這個時序，建議在實際寫檔前發現同篇已開進編輯模式就停止這次寫入，提示重試。

#### R2｜選到編輯器後切回閱讀模式，仍可寫進隱藏編輯器

**軸：規格。證據：基準與待審版均在記憶體探針重現，切換時的宿主行為待驗證。**

- **觸發、預期與實際**：確認後先選到編輯分頁，在 `vault.read()` 等待期間把它切到閱讀模式。預期應重新確認分頁能否用來寫入，或停止並請使用者重試。兩版都呼叫該 view 的 `save()` 一次。在依既有實機紀錄模擬的閱讀模式存檔行為下，隱藏編輯器變成「啟用」，磁碟仍是「草稿」，回「這篇筆記剛剛改過，請再按一次」，新增狀態紀錄 0 行。`editorOf()` 驗證路徑及文字，沒有再次確認模式。 `src/obsidian/deck-status.ts:46` · `src/obsidian/save.ts:96` · `tasks/release-0.6.0.md:142`
- **真實路徑、機率與處理**：估計低頻，需要確認後立刻切換，或 I/O 等待拉長。穩定停在閱讀模式時，舊版寫入隱藏編輯器已有 Windows 實機紀錄。這次切換時是否保留同一個 view 和 editor，待驗證。建議和 R1 一起測。若實機成立，在套用交易前確認同篇仍開在編輯模式，失效時用既有的重試提示。

#### R3｜同篇有兩個編輯分頁，只檢查第一個

**軸：規格。證據：基準與待審版均重現分頁文字分岔時的行為，真實分岔待驗證。**

- **觸發、預期與實際**：同篇有一個閱讀分頁和兩個編輯分頁，列舉順序中的第一個編輯分頁與磁碟相同，第二個有未存文字。預期第二個分頁的未存修改也會擋住操作。兩版都用第一個編輯器存成「暫停」並記一行，沒有提示。第二個編輯器的文字在替身中仍保留。既有 Windows `lock` 探針顯示同視窗的兩份編輯內容會跟上，尚未涵蓋變更剛發生的瞬間或跨視窗是否會分岔。 `src/obsidian/deck-status.ts:46` · `src/obsidian/dev-ids.ts:210`
- **真實路徑、機率與處理**：既有 Windows 探針已驗到 `getLeavesOfType('markdown')` 能看見彈出視窗分頁。估計低頻，還需要兩個編輯分頁真的在檢查當下持有不同文字。建議 Windows 補測時順手涵蓋。若能取得分岔的編輯內容，再把未存檢查套到同篇所有編輯分頁。 `src/obsidian/dev-events.ts:51` · `tasks/obsidian-1.15-compat.md:32`
