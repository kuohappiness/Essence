# Essence 討論

一件事從點子到完成的路線、每類文件的狀態行與連結寫法，見 `docs/agents/workflow.md`；這裡只寫怎麼討論。

1. **一輪只問一題**：先把要決定的事列成決策樹，挑不依賴其他未決題目的最上游那一題問，等使用者回答再問下一題。不要一輪列出多題。
2. **先查再問**：提問前查相關的舊決定（已知 D-ID 用 `node tools/decisions-index.ts D-xxx`，不知道時讀索引裡相關的主題），只讀相關的幾條；新提案和舊決定衝突時，明講是哪一條、為什麼值得重談。repo 裡查得到的事實自己查，不問使用者。
3. **提案不是決定**：每題附上你的建議答案，標 💡。
4. **先問會不會明顯更好，再比不做**（D-177、D-153）：每個提案寫出 ① 優勢、不做會怎樣：具體壞在哪、多常發生、影響誰（學生、家長或開發）；② 做的代價：新增的程式、文件、測試，以後要維護的，使用者要多學的；每一項寫出解決得了嗎、怎麼解決；③ 更小的做法：只改現有的、延到第二階段，或先在試作場試一次，和完整做法差距不明顯就選它。優勢明顯、代價解決得了就建議做，工作量不算理由；好處很小又費力，或代價解決不了，才建議不做。
5. **優先刪減**：每題談完，檢查有沒有東西沒有讓結果明顯變好，可以刪掉或移出 v1。
6. **用真實教材例子**驗證抽象設計；試一次就知道的問題，建議改到試作場（`experiments/`）做，不在對話裡猜。
7. **重大決策的第一輪各自獨立**（D-215 第 4 點）：選項還開著的題目，討論稿依序是〈提問稿〉（事實、來源、問題、回答格式，不放 Claude 的選項排序與建議）→〈第一輪：Claude〉〈第一輪：Codex〉→〈第二輪：交叉〉（Codex 站「不做」那一方）→〈請使用者決定〉。Claude 的第一輪答案在呼叫 Codex 之前寫好、存在檔案外（scratchpad），Codex 交回後才一起放進討論稿。回答格式：第一行寫「獨立／交叉」與模型，再寫三行摘要、建議、理由、風險與解法、替代方案、把握程度、缺少的資訊。提案已成形、要找洞的照舊一輪一輪查。
8. **兩邊的考量分開寫**：Claude 與 Codex 討論出選項、要請使用者決定時，先分別寫出兩邊的考量與不採用的代價（一致就寫一致，有分歧就標出來），最後才給推薦。
9. **問清楚範圍**：使用者說「現在不用考慮某件事」時，先問是暫時不做還是以後都不做、影響哪個範圍，再動已經寫好的檢查或測試。
10. **研究出處是加分**：學習方法、排程、出題方式的提案，有把握又能幫助判斷的研究可以附上（作者、年份、一句結論，不誇大）；沒有合適的就不寫，不是固定格式。

## 結束

- 談定的題目：用 Skill tool 載入 "essence-decision"，先判斷要不要寫成 D-ID（小事寫「使用者 YYYY-MM-DD 同意」在那件事現在的位置）。
- 沒談完：還沒解的問題與目前傾向寫在主文，同一個問題只有一份主文，依序選：已交付實作且沒另開討論的 → 任務說明（`docs/tasks/`，外掛專用的在外掛的 `docs/tasks/`）；Claude 與 Codex 正在往返的 → 該討論稿；其他已展開的規畫 → `docs/plans/`；短點子 → 那個外掛的 `docs/backlog.md`〈待處理〉，跨外掛的在最上層（D-141）。新的一站開頭寫「來自」，上一站加「→」。
- 主文的狀態行照〈入口的狀態行〉寫新格式（狀態、下一步、等誰三欄）。roadmap 的狀態板與〈已完成〉不手改：改了狀態行就跑 `node tools/roadmap-sync.ts`，再 `git add` 改到的 roadmap。
- 沒有討論稿的重要討論：結束時在 `docs/archive/discussions/` 新增 `YYYY-MM-DD-主題.md`（摘要，不冒充逐字紀錄），更新該目錄 README 的索引；有討論稿的不另寫（D-106、D-143）。
