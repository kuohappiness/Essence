# 直接呼叫 AI 之後的多段審查：模糊的判斷交給窄的 AI 檢查

狀態：討論中｜下一步：Codex 找漏洞（§6），之後交使用者決定｜等誰：Codex

來自：[三層架構檢討](2026-11-25-three-layer-review.md) §9（使用者 2026-11-25 第 8 點）

## 1. 問題

使用者 2026-11-25：「我目前推論要解決上述的問題就是利用API多段的機制，把審核權交回給AI審查，因為太多錯誤存在模糊判斷空間，很難用程式完美的擋掉，你的看法呢? 如果你也同意，那方向可能要調整比較大」。

前提：家長不會改題目（使用者 2026-11-25），草稿幾乎直接進孩子的複習；畫面照樣呈現，想改的家長可以改，但那是彈性，不是防線。

## 2. 證據

**整份重審沒有用**（[比較測試〈結果〉](../tasks/rule-restructure-test.md#結果)「第二道查核」）：另開對話照同一套規則整份再看一次，必備漏掉的 3 項抓到 0 項，「部分」只抓到一成多；改壞 2 處，其中一處把題目移到判準不合的已有目標；每份 13～22 萬 token。多抓的有一半是真的問題（英文找到 9 處兩張卡互相洩漏，評審只記到 1 處）。

**窄的檢查有用一部分**（2026-11-25 在使用者電腦離線測，只用第一輪已評分的原稿；設計照[三層架構檢討](2026-11-25-three-layer-review.md) §5 測試 2，開跑前凍結；逐份結果只在使用者電腦）：

| 檢查 | 怎麼做 | 結果 | 門檻 |
|---|---|---|---|
| 盲解抓多解 | 抽出英文打字題的題幹（拿掉答案、詳解、錨點），另開對話寫最自然的兩個答案，不在答案欄的標「可能多解」 | 791 題標 174 題。兩位評審都記的 8 題抓到 5 題（63%）；只一位記的 186 題抓到 92 題（49%）；沒人記的旗標抽 20 筆，18 筆是真的多解（同義片語、冠詞或代名詞不同、縮寫） | 過（一半以上；沒人記的不超過抓到的一倍） |
| 加題核對 | 給那個目標的全部題目加新題，只問「同一個判準、同一個意思嗎」，只能降成候選 | 227 筆加題：已知加錯 5 筆抓到 2 筆，漏的 3 筆都是文法目標換了時態條件、答案形式相同；對的被降級 4 筆（1.8%），逐筆看都說得出理由 | 沒過（要全部抓到） |
| 程式意思核對（[外掛任務](../tasks/rule-restructure-plugin.md) §4-2） | 英文單字加題，新答案的中文和舊答案沒有共同的字就標 | 只查得到單字目標 163 筆：已知加錯抓到 1 筆（另 4 筆是文法目標），誤標 1 筆 | 對照 |

用量：盲解 12 次 84.6 萬 token、加題核對 15 次 106 萬 token，每次 11～34 秒；大部分是測試時 subagent 每次固定帶的約 6.5 萬字說明，改用 API 只送必要的會少很多，實際多少要接上 API 才量得到。

## 3. 提案

**分工**：

| 誰 | 管什麼 | 例子 |
|---|---|---|
| 規則 | 上游：核心邏輯、學習地圖、出口收窄、怎樣算考到 | 漏項大多在規則給的出口被送走（三層架構檢討 §1.2），後面的審查補不回來 |
| 程式 | 機械的：格式、ID、同名、數量、完全相同 | 快、準、不花 token |
| 窄的 AI 檢查 | 模糊的：一次只判一件事，另一個對話，看不到不需要的東西 | 盲解抓多解、單字加題的意思 |
| 家長 | 彈性 | 畫面照樣並排，想改可以改 |

**三個條件**：

1. 一次只判一件事，不整份重審（整份重審改壞 2 處、漏項 0/3）。
2. 只能降級或標記：加題降成候選、題目標成「要改」；不准自己另立目標或改寫題目。例外與處理見下一點。
3. 不取代規則：規則仍是品質的主要來源，檢查只補規則做不到的那一類（出題的 AI 知道答案，自己想不到別的答法）。

**盲解找到的另一個說法怎麼處理**（要 Codex 找洞）：抽查 20 筆有 2 筆不是真的對，直接收進答案欄會讓錯的答案也算對。候選做法：

- 甲：另一個獨立的檢查也寫出同一個說法才收進答案欄；只有一個寫出的，退回出題的 AI 改題（鎖住或換句子），改完再盲解一次。
- 乙：一律退回出題的 AI，由它決定收進答案或改題，再盲解一次。
- 丙：標記給家長。不採用：家長不會改。

💡 傾向甲。收進答案欄要等使用者選完「字數不同的兩個說法」那張決定卡（改不改 D-122）。

**順序**：

1. 手貼期間：規則照下一版修；程式的機械檢查與意思核對先用著；不加手貼的步驟。
2. 外掛直接呼叫 AI（分支 `claude/project-thread-q0jv5f` 的 `docs/tasks/ai-client.md`，審查中）接上 Cards 的優先順序往前拉：窄檢查、兩段送法、分科分段送都卡在它。
3. 接上後第一個放進流程的是盲解：英文審稿量七到八成是多解（[英文候選刪減對照](2026-11-25-english-candidate-diff.md) §3）。
4. 單字的加題改用 AI 核對，程式核對留著當沒有 API 時的備援。
5. 文法目標的加題核對另外設計再測（例如先讓檢查者寫出那個目標的判準，再拿新題比）。
6. 洩漏檢查（另一個對話只看題幹與同池其他卡，答不答得出）：整份重審找到 9 處、評審只記 1 處，值得做成窄檢查，要先測。

**和不做比**：不做就只能靠規則與程式。規則擋不了出題的 AI 自己想不到的答法（第一輪英文的多解，現行與候選都有），程式判斷不了意思；家長又不會改。孩子答對被判錯，排程跟著錯，正是北極星最在意的時間與正確。

**代價**：每課多幾次 AI 呼叫的費用與時間（接上 API 後實測再定上限）；流程多幾段，要處理某一段失敗或逾時（照 `code-quality` 寫規格時的逾時結局）；檢查本身會錯（盲解抽查 2/20、加題核對漏文法 3/5），所以只給降級與標記的權限，最壞是少收一題或少加一題。

## 4. 不用改的

三層架構（核心講原則、模組各自負責，比較容易配「一段一個窄任務」）；程式的機械檢查；手貼流程（沒有 API 時照舊能出正確的卡）；[D-236](../../../../docs/decisions.md#d-236-製卡規則比較測試的評估對齊北極星錯誤分輕重量孩子的時間評學習地圖) 的評估要量「整條流程最後交到孩子手上的卡」，不只第一次生成。

## 5. 還要確認的

- API 的費用與家長設定金鑰的摩擦（「讓外掛直接呼叫 AI」那一串）。
- 每一種窄檢查用哪個模型、什麼推理等級最划算。
- 盲解的旗標在比較點選、文法翻面等非打字題要不要也做（這次不在範圍）。

5. 和不做比，代價有沒有漏算（費用、時間、失敗處理、手機）。
