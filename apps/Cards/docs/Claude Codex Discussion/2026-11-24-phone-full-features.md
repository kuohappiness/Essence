## 提問稿

### 使用者已定的（不重開）

- 2026-11-23：「我有時候會在手機工作，我想開啟手機上『AI 製卡』的功能。」
- 2026-11-24，回答「手機上的 AI 製卡要做到哪一步」（選項是只到存成草稿、也能按啟用、先不做）：「**手機擁有全功能，但預設都關閉，要去設定頁面打開**。」
- Claude 的讀法（細節請使用者確認的部分，留到〈請使用者決定〉）：電腦上家長用的製卡與管理功能，手機都要有；每台手機在自己的設定頁打開，只存在那台裝置、不隨 vault 同步（同 `src/ui/prefs.ts` 用 `app.saveLocalStorage` 的做法，例如預覽按鈕 [D-222](../../../../docs/decisions.md#d-222-預覽按鈕在電腦預設打開)）；沒打開的手機（孩子的 iPhone、孩子們共用的 iPad）照現在。

### 要回答的問題

1. **逐項**：〈現況與事實〉第 1 點的每個電腦專用功能，在「打開了的手機」上怎麼做：照電腦一樣開、改做法才開，或手機做不到（寫明原因，以及使用者在手機上看到什麼）。
2. **核心**：打開的手機改寫已有的卡組、配學習目標 ID 時，[D-134](../../../../docs/decisions.md#d-134-學習目標-id-的補上時機與保護) 的原則（「弄丟或接錯複習紀錄，不能靠家長的習慣避免，由程式擋住」）怎麼守住；守不住的部分，壞在哪、多常發生、影響誰、怎麼偵測與補救。
3. **備份**：[D-150](../../../../docs/decisions.md#d-150-備份與還原) 第 3 點（這台沒有成功的備份就不改寫卡組）在不能備份的手機上怎麼辦。
4. **分批與時程**：要不要分批、每批放什麼；和 0.7.0（12/2 之後，併一次 iPhone 實機測試）的關係；哪些要先在試作場或 iPhone 實機量過才能決定。
5. **決定**：要改或新增哪些 D-ID（產品範圍、ID、備份都在 D-215 第 5 點「要寫成 D-ID」的範圍）。

使用者的原則：有實質優勢、代價解決得了就做，工作量不是理由（[D-177](../../../../docs/decisions.md#d-177-先問會不會明顯更好優勢明顯代價解決得了就該做)）；每個選項和「不做」比較（[D-153](../../../../docs/decisions.md#d-153-每個新決定與新任務先和不做比較)）；改版改不回來的測試做足（[D-195](../../../../docs/decisions.md#d-195-測試分兩類改不回來的做足其餘延後但不漏)）；使用者會碰到的流程做進外掛畫面、不用 Git 與命令列。

### 可以考慮的選項（只是起點，不代表排序）

第 2 題：

- 甲：打開的手機和電腦一樣寫（同一套寫入門檻），衝突靠現有的偵測處理：D-134 的「原本的 ID 不見、同時出現沒見過的 ID 就先停出、家長選」，[D-157](../../../../docs/decisions.md#d-157-重複的學習目標-id先停家長選) 的「重複 ID 全部先停、家長選」。
- 乙：打開的手機只寫「還沒有複習紀錄」的東西：建新檔（AI 製卡）、改草稿與補草稿的 ID、草稿改成啟用、改狀態；已啟用卡組的內文與 ID 仍只在電腦寫（加深、引言框的加入、存檔補 ID 遇到已啟用的卡組時，手機上說明要到電腦做）。和使用者說的「全功能」有落差，要比較的是落差值不值得。
- 丙：手機全寫，另加一道程式擋的防線。例如每台裝置追加寫一份「改了哪一篇、改之前與之後的雜湊、時間」的紀錄（和複習紀錄一樣一台一份、只追加）：改寫前看別台的紀錄裡這一篇有沒有更新的版本還沒到，有就先不寫；事後發現兩台從同一版各改了一次（分叉），提醒家長。
- 丁：其他你認為更好的。

第 3 題：手機不擋；電腦把「最近一次成功的備份（版本、時間）」寫進 vault 讓手機看，同一版有備份才讓手機改寫；其他。

### 現況與事實

請自己核對。

1. **電腦專用的家長功能**（`apps/Cards/src/main.ts`，用 `Platform.isDesktopApp`／`Platform.isDesktop` 分）：
   - 存檔按鈕、離開筆記時補 ID、鎖住 ID、重複 ID 與 ID 不見時的處理：`wireIds`（D-134、D-157）。
   - AI 製卡：命令與左側圖示，`createAiCards`、`wireAiCards`；程式註解「AI 製卡只在電腦（D-039）」。
   - 加深這一節、提醒一區的加深列：`createDeepen`、`wireDeepen`（[D-194](../../../../docs/decisions.md#d-194-加深的主動提示記穩了三分之一就問按一下才做)）。
   - 引言框的「加入」：`createIntroRunner`、`wireIntroButtons`。
   - 卡組標題列的「啟用」（草稿改成啟用）：`wireDeckActions` 的 `activate`；目錄的暫停／恢復：`openEntry` 的 `setDeckStatus`。
   - 入口的提醒一區與狀態列：`reminders: Platform.isDesktop`（[D-163](../../../../docs/decisions.md#d-163-入口與目錄的四批開法全部卡的一輪與提醒一區) 第 5 點：手機沒有這一區）。
   - 備份與還原：D-150、[D-148](../../../../docs/decisions.md#d-148-電腦專用的主機接點)（備份寫在 vault 外，用 Node 的 `fs`，在 `src/desktop/`）；手機的設定頁備份一區只寫「備份在電腦上做」（`src/obsidian/settings.ts`）。
   - 已經是每台裝置自己的開關、手機預設關的：預覽按鈕（D-222）。
2. **寫入門檻**：`apps/Cards/src/state/writes.ts` 的 `blockedNow()`，`fillIds` 為 false（`main.ts` 建 state 時傳 `fillIds: Platform.isDesktopApp`）就回 `phone`，所有改寫卡組與 AI 製卡的建檔都擋。電腦上之後依序看：讀完了沒、關閉、還原中、這台有沒有成功的備份（D-150 第 3 點）、有沒有讀不到的卡組或紀錄（[D-154](../../../../docs/decisions.md#d-154-雲端佔位檔讀不到時預防當下說清楚先實測)）。
3. **AI 製卡存草稿只建新檔**：`apps/Cards/src/core/ai/publish.ts` 的 `PublishIo` 只有建立（原文、草稿卡組、快照），沒有修改；「加進已有的學習目標」是寫在新草稿裡的連結，不改舊卡組（[任務說明 §5](../tasks/ai-cards-mvp.md#5-存草稿與快照要格式查核)）。啟用要改那篇草稿的 `狀態`（§7）。加深會把新目標與 ID 寫進已有的卡組（`src/core/ai/deepen-write.ts`）。
4. **ID**：6 個字元、字母表 31 個（`src/core/deck/assign.ts`）；配號避開所有卡組、複習紀錄出現過的 `lt`，以及**這台裝置**預留的（AI 製卡與加深沒完成的工作、不再配出的清單，存在 `localStorage`，不同步，`src/ui/prefs.ts`）。建卡組的當下再核對一次 ID 沒被占用（`aiCreateDeck`）。
5. **D-134 的理由**：「兩台裝置同時改同一篇，iCloud 只留一邊，兩邊各配一個 ID 時，另一邊的作答就對不到目標。」D-134 的代價裡寫了「擋不住 Obsidian 以外的編輯器與其他外掛直接寫檔；兩台電腦離線改同一篇的既有風險不變」。手機現在仍可以用 Obsidian 直接改筆記，只是外掛不在手機上配 ID（`apps/Cards/docs/product.md`〈不做〉）。
6. **iCloud 的衝突**：[D-199](../../../../docs/decisions.md#d-199-040-帶著電腦設定檔的衝突上線下一版先修)：電腦寫的 `.obsidian/.../data.json` 每次都被 iCloud for Windows 改名成衝突副本，傳到 iPhone 變成刪除，兩台的設定一起回預設、沒有提示（修法 [D-201](../../../../docs/decisions.md#d-201-設定改存-vault-裡的一般檔電腦不再寫-datajson)）。iPhone 與電腦**兩邊都改同一篇 `.md`** 時 iCloud 留哪一邊、會不會出衝突副本、副本叫什麼，沒有量過。D-154 的 Windows 實測：iCloud 停著時追加的行不上傳（`apps/Cards/docs/tasks/icloud-placeholders.md`〈結果〉W1）。
7. **裝置**：家長在電腦製卡；這次要打開的是家長自己的 iPhone。孩子用自己的 iPhone（不同 Apple 帳號，iCloud 共享同一個 vault 資料夾），孩子們共用一台 iPad；同一個 vault 的外掛在每台都會載入。孩子在手機上也能打開設定頁。
8. **手機上的技術點**（都還沒在 iPhone 上驗過）：
   - 提示放進剪貼簿用 `navigator.clipboard.writeText`，在按鈕的點擊裡同步呼叫（`buildPrompt` 是同步的）。最近三份真實提示 79.7 KB、94.1 KB、111.4 KB，回覆 26～57 KB（提早試用 U4～U6）。外掛在 iPhone 上從沒用過剪貼簿。
   - 待貼回的工作在按「複製提示」的當下就存進這台的 `localStorage`；Obsidian 在背景被系統關掉，重開還能「接著貼回」。貼到一半的文字只存在記憶體。
   - 鎖住 ID 是電腦版 Obsidian 編輯器（CodeMirror）的擴充，D-134 的代價寫明要在電腦版逐一驗證各種編輯；iOS 的中文輸入沒驗過。
   - Obsidian iPhone 版的外掛讀寫不到 vault 以外的地方。
9. **時程**：使用者定 12/1 前不換版；0.7.0 在 12/2 之後做，和一次 iPhone 實機測試一起（`apps/Cards/docs/plans/early-trial.md`）。
10. **審查的 P1**（`AGENTS.md`〈Code Review Rules〉）：學習目標 ID 或複習紀錄遺失或重複、排程算錯、寫回筆記不冪等。

**必讀**：D-004、D-019、D-039、D-134、D-148、D-150、D-154、D-157、D-163、D-194、D-199；`apps/Cards/docs/tasks/ai-cards-mvp.md` §5、§7；程式 `src/main.ts`、`src/state/writes.ts`、`src/obsidian/ai-cards.ts`、`src/core/ai/publish.ts`、`src/ui/prefs.ts`。查決定用 `node tools/decisions-index.ts D-xxx`。

### 要特別判斷的

- 第 6 點沒量過的 iCloud 行為，會不會改變結論；要量的話，在 iPhone 實機測試還是試作場量、怎麼量。
- 開關在設定頁、孩子也能自己打開：這樣夠不夠，要不要多一道。
- 手機上不鎖 ID 時，手機改卡組的風險和現在（手機能改筆記、不配 ID）比，多了什麼。
- 加深的主動提示（D-194 在電腦的提醒一區問）、提醒一區本身，手機打開後要不要出現。
- 只有一台手機、沒有電腦的家庭：這個開關會不會讓人以為只用手機就夠（D-150 的備份與還原仍只在電腦）。

## 第一輪：Claude（獨立回答，寫於呼叫 Codex 之前）

第一輪：獨立回答（Claude，Opus 5.5、xhigh，2026-11-24）

**三行摘要**

- 只建新檔或只改一行狀態的（AI 製卡、啟用、暫停／恢復、提醒一區）在打開的手機上照電腦做，第一批放進 0.7.0。
- 改已有卡組的內文與配 ID 的（存檔補 ID、引言框的加入、加深、重複與不見的 ID 的處理）不會帶來新種類的錯，但會讓「兩台都改同一篇、iCloud 只留一邊」更常發生；建議也開，排第二批，先在同一次 iPhone 實機測試量 iCloud 的實際行為，再決定要不要加偵測。
- 備份與還原在手機做不到（外掛寫不到 vault 外），照舊只在電腦；第一批不需要備份閘門，第二批改寫內文前要看到「同一版在電腦有成功的備份」。

**建議**

第 1 題（打開的手機）：

| 功能 | 打開的手機 | 理由與做法 |
|---|---|---|
| AI 製卡（存成草稿） | 照電腦，第一批 | 只建新檔（`PublishIo` 沒有修改）。配號照舊避開讀得到的全部 ID，有讀不到的卡組或紀錄就照舊擋（`unread`）。 |
| 卡組標題列的「啟用」、目錄的暫停／恢復 | 照電腦，第一批 | 只改一行 `狀態`；寫入走同一列、同一套門檻。 |
| 入口的提醒一區（含加深列） | 照電腦，第一批 | 只讀、按了才做；手機沒有狀態列，只在入口出現。 |
| 預覽按鈕 | 已有自己的開關，不動 | D-222。 |
| 存檔按鈕、離開時補 ID、重複 ID 與不見的 ID 的處理 | 照電腦，第二批 | 見第 2 題。 |
| 引言框的「加入」、加深這一節 | 照電腦，第二批 | 寫進已有的卡組（含已啟用），見第 2 題。 |
| 鎖住 ID | 手機先不鎖，iPhone 實機驗過中文輸入再開 | 不鎖時和現在一樣（手機本來就能改筆記）；D-134 的解析容錯與「不見的 ID 先停出」照樣在手機上作用。 |
| 備份、還原 | 做不到 | Obsidian iPhone 版的外掛寫不到 vault 外（D-148）。設定頁照舊寫「備份在電腦上做」，開關的說明加一句。 |

開關：設定頁一列「這台裝置也能製卡與改卡組」，預設關，存這台的 `localStorage`。打開時跳一個確認（「這是給家長的功能：會在這台裝置建卡組、改卡組、配學習目標 ID」），擋孩子隨手點開；不另設密碼（孩子本來就能在 Obsidian 改筆記，多一道密碼只增加家長的摩擦）。

第 2 題：選甲（打開的手機和電腦一樣寫），分兩批，第二批之前先量。

- 實機測試（0.7.0 那一次，用測試 vault）加一項：電腦與 iPhone 在同步之前各改同一篇卡組（一邊加目標、一邊改別行），記下 iCloud 留哪一邊、有沒有衝突副本、副本叫什麼、另一台看到的是修改、副本還是刪除。iPhone 斷網改、再連網也做一次。
- 量到「會出衝突副本」：D-157 的重複 ID 先停、家長選就接住，不會接錯紀錄，第二批照甲做。
- 量到「默默留一邊」或「變成刪除」：第二批加一個便宜的偵測：有作答紀錄的學習目標在同步進來的修改後不見了（不在任何一篇），提醒一區列出那一篇與時間，請家長在電腦用還原找回（D-150 第 7 點已會列出 ID 的差異）。不做丙的改寫日誌。

第 3 題：第一批不擋（新檔與一行狀態，壞了也不影響已有的卡組內文）。第二批：電腦每次備份成功，寫下「哪一版、什麼時候」到 vault 裡一個只由電腦寫的小檔；打開的手機改寫已有卡組前，看同一版有沒有成功的備份，沒有就停下來說「先在電腦打開一次 Obsidian，讓它備份」。放在哪個檔、格式，在第二批的任務說明定，開工前做格式查核。

第 4 題：

- 第一批（0.7.0）：開關、AI 製卡、啟用、暫停／恢復、提醒一區；手機版的視窗排版。iPhone 實機驗：剪貼簿放 111 KB 的提示、ChatGPT／Claude／Gemini 的 iPhone App 收得下、從 App 的程式碼區塊複製 57 KB 的回覆貼回、切到 AI App 很久之後 Obsidian 被系統關掉還能接著貼回。剪貼簿放不進去時的退路：視窗裡顯示整份提示、附「全選」，讓家長自己複製（寫進任務說明，實機失敗才做）。
- 同一次實機量 iCloud 兩邊都改同一篇（第 2 題）。
- 第二批（量完）：存檔補 ID、引言框的加入、加深、重複與不見的 ID 的處理、鎖住 ID 的 iPhone 驗證、第 3 題的備份標記。
- 為什麼分批：第二批的防線要看量到的 iCloud 行為才定，先做可能做錯；0.7.0 還背著考前抽測（1/11 前裝好），整包一起做會壓到提早試用。第一批已經涵蓋使用者在手機上最可能做的事（拍課本、AI 製卡、存草稿、啟用）。

第 5 題：新的一條 D-ID「家長的手機也能製卡與改卡組，每台自己打開」，修改 D-039（〈不做〉拿掉「手機上的製卡介面」）、D-134（補 ID 的「只在電腦」改成「電腦與打開的手機」）、D-163 第 5 點（提醒一區）、D-004／D-019 的分工描述（電腦製卡 → 電腦或打開的手機）、D-194（加深的提示也在打開的手機）；D-150 第 1 點不變、第 3 點補手機的規則（第二批）。`product.md`〈不做〉、`architecture.md`〈4. 平台與裝置〉跟著改。

**理由**

- 使用者的需求是「不在電腦旁也能做」，最常見的是用手機拍課本、在 AI App 送出、貼回存草稿、看完啟用：第一批全部是只建新檔或改一行狀態，沒有碰到 D-134 擔心的配 ID。
- 第 2 題的風險不是新種類：手機現在就能改卡組筆記（`product.md`〈不做〉），父母在手機改到一半、電腦同時補 ID 時，iCloud 留一邊就可能讓電腦補的 ID 不見；D-134 的代價已經接受「兩台電腦離線改同一篇的既有風險」。手機也配 ID 是把同一種風險從單向變雙向，次數變多、種類不變。要兩台在同步完成之前改同一篇才會發生，打開的只有家長自己的手機。
- 丙（改寫日誌）是新的檔案格式、要寫格式說明與第 1 類測試，只能縮小一個本來就存在的窗口、事後也拿不回被蓋掉的內容（只存雜湊）；在還不知道 iCloud 實際怎麼處理之前，代價大於好處。
- 乙（已啟用的卡組手機不寫）守得最緊，但和使用者說的「全功能」有落差：加深、引言框的加入都要回電腦；使用者已經選了全功能，風險又不是新種類。

**風險與解法**

- iCloud 默默留一邊，已經作答的目標不見、紀錄對不到：量過再決定；最壞是那幾個目標的進度要從備份找回，紀錄本身只追加、不會刪（D-035）。解得了，但要家長在電腦操作一次。
- 孩子自己打開開關：確認視窗擋隨手；真的打開，最多建草稿或啟用卡組（孩子本來就能改筆記）。解不了「刻意打開」，但後果可以還原。
- 剪貼簿或 AI App 收不下長提示：實機才知道；退路是手動全選複製，或把提示拆成兩段（後者會改規則組的送法，不建議先做）。
- 手機不鎖 ID：和現在一樣；鎖的擴充先在 iPhone 驗過中文輸入。
- 只有手機的家庭以為不用電腦：開關說明寫清楚備份與還原只在電腦；這類家庭不是 v1 的對象。

**替代方案與它們輸在哪**

- 不做：使用者不在電腦旁就不能製卡；使用者明確要求，第一批的代價小。
- 乙：守得最緊，但和使用者要的全功能有落差，而且擋的是一個已經存在的風險種類。
- 丙：防線最完整，但新格式、新測試，在 iCloud 行為未知時可能白做。
- 一次全部做進 0.7.0：第二批的防線沒有依據，還會壓到考前抽測。

**把握程度**：中。第一批高（只建新檔、改一行狀態，程式路徑和電腦相同）；第二批取決於沒量過的 iCloud 行為。

**缺少的資訊**

- iPhone 與 Windows 兩邊都改同一篇 `.md` 時 iCloud 的實際行為（會改變第二批要不要加偵測）。
- iPhone 的 Obsidian 能不能用 `navigator.clipboard.writeText` 放 100 KB 以上的文字；各家 AI 的 iPhone App 收不收得下。
- 使用者在手機上會不會常改已啟用的卡組（如果幾乎只做 AI 製卡與啟用，第二批可以晚一點）。

#### 2. 用單一寫入端守住 D-134

每個 vault 指定一台電腦，由它負責 Cards 的正式卡組寫回、配 ID 與發布。同一個 vault 的手機、iPad 和其他電腦都能複習。開啟手機家長模式時，建議在設定頁由指定電腦配對核准一次，並可撤銷。**本機開關能防同步誤開，單靠它防不了孩子自行啟用。** 配對可防未核准裝置透過 Cards 送出管理操作。對於已能在共享 vault 直接改 Markdown 的人，外掛仍有原本的權限限制。 [prefs.ts](../../src/ui/prefs.ts) · [D-134](../../../../docs/decisions.md) · [產品定義〈不做〉](../../docs/product.md)

- **送出與套用。** 手機先把工作保存在本機。每次請求以獨立檔案同步，帶操作識別碼、對象、基準雜湊與操作內容。電腦在既有寫入佇列內重讀，依現行規則檢查載入、版本、備份、讀不到的檔、ID 占用和待處理衝突。基準不符就讓家長看差異。等待逾時維持待處理，重試沿用同一操作識別碼。更換寫入端前要停掉舊端，舊版桌面外掛若仍能寫，就先擋住手機正式提交。 [writes.ts 寫入閘門與佇列](../../src/state/writes.ts) · [寫入當下重查](../../src/state/writes.ts) · [D-154](../../../../docs/decisions.md)
- **留下可核對的版本與身分。** 改寫舊篇前保存可復原的舊內容，並留下跨重啟可讀的寫入憑據、原版本、新版本與受影響的目標。重開、斷線或同步換序時，讀到的版本對不上憑據就暫停受影響的目標與新作答，保留其他篇的複習。復原時讓家長比對內容，能確定身分才接原 ID。遇到重複也先全停，且在身分仍有疑問時，不能因為只剩一份就自動恢復。這是 D-134、D-157 需要補上的行為。 [D-134 的待處理期限與還原規則](../../../../docs/decisions.md) · [D-157 的停出與恢復](../../../../docs/decisions.md)

#### 3. 備份由實際寫回的電腦負責

維持 D-150 的每月、手動、新版首次寫入前備份。手機能暫存未發布的工作。**正式建檔或改寫仍由同一台通過備份閘門的電腦執行。** 改寫已有卡組再核對要改的那一版是否有可還原的內容，缺少時先保存並讀回核對。月備份保護 vault 的整體資料，這一步保護該次改寫的起點。還原沿用外掛逐檔比對，複習紀錄只補不刪。 [D-150 第 1–8 點](../../../../docs/decisions.md) · [main.ts 桌面備份啟動與寫入門檻](../../src/main.ts)

只有手機的家庭可以複習、預覽，以及保存在本機的未發布製卡工作。開關旁寫清楚正式發布、備份與還原需要配對電腦。若產品要支援純手機正式製卡，要先找到能在手機建立獨立備份、讀回核對、再還原的做法，並重新定 D-150。這輪已有的程式與決定只支持桌面端。 [D-148](../../../../docs/decisions.md) · [D-150](../../../../docs/decisions.md)

### 理由

1. **本機寫入佇列無法看見尚未同步的變動。** `blockedNow()` 擋平台、載入、關閉、還原、備份與已知讀不到的檔。`create()` 在寫入回呼內還會重查名稱、ID 與已知待讀的變動。兩台都讀得到本機檔案、卻都還沒看到對方的寫入時，這些檢查仍可能各自通過。把 `fillIds` 放開也會一起打開既有卡組與 AI 建檔的入口，所以應分開處理手機送出操作和正式寫回。 [writes.ts](../../src/state/writes.ts) · [create() 寫入回呼](../../src/state/writes.ts) · [state 的平台設定](../../src/main.ts)
2. **AI 存草稿是最先能帶來收益的一段。** `PublishIo` 對原文、卡組和快照只提供建立。補到已有目標的內容先在新草稿存連結。啟用及加深則會修改既有檔，加深雖驗證本機寫前寫後的正式目標原樣保留，同步晚到仍可能換掉整篇。先交付手機能生成、審核、提交及啟用的閉環，家長外出就能推進製卡。 [PublishIo](../../src/core/ai/publish.ts) · [AI 製卡 §5](../../docs/tasks/ai-cards-mvp.md) · [加深的寫回驗證](../../src/core/ai/deepen-write.ts)
3. **最嚴重的情境完全不需要隨機撞號。** 手機從舊版加出目標 A，電腦從同一版加出目標 B。兩端各自發布，有孩子收到 A 後已作答，後來收斂成只有 B。A 的作答行可能還在，原目標卻失聯。D-134 必須有舊版可比，且「舊 ID 不見」與「新或缺 ID 出現」同時成立才會停出。重啟後、整篇消失、只收到其中一版，或兩個合法 ID 互換，都不能依賴這個條件。D-157 也要兩個目標都讀到才會擋。只剩錯的那份時，還可能接錯進度。涉及 ID 失聯或錯接的情境按 P1 驗。 [D-134](../../../../docs/decisions.md) · [D-157](../../../../docs/decisions.md)
4. **撞號少見，已知占用和全域占用仍是兩回事。** `31^6 = 887,503,681`。假設兩端各抽 100 個、抽樣近似均勻且獨立，至少一次跨端撞號約 **0.00113%**。這只是抽樣估算。唯讀記憶體探針以相同亂數呼叫 `newId`，兩台各用空集合時都得 `aaaaaa`，同一台把它列入占用後得 `aaaaab`。另以替身回傳區塊 ID 測到 `publish.ts` 的 `writtenIn`，異文同 ID 在 `pending` 判為不同一份，在 `started` 判為已寫成。這是中斷後把別端異文當成本次產物的可能路徑，正式流程重現待驗證。由單一寫入端配號，並保留該次操作的寫入證據，可避免用「ID 找得到」單獨證明這次寫過。 [assign.ts](../../src/core/deck/assign.ts) · [本機的未完成工作與不再配出清單](../../src/ui/prefs.ts) · [發布的身分核對](../../src/core/ai/publish.ts)
5. **iCloud 的證據足以要求實測，還不足以估事故機率。** D-199 的三次失敗發生在 `.obsidian/data.json`。D-201 的一般 vault 設定檔在 V3 雙端各改一項後只留其中一份，沒有副本。Windows 的 W1 則測到 iCloud 停止時追加可能不上傳，後續再追加可把前一行帶上去，而單端整篇改寫 `.md` 在重啟後約 150 秒上傳。三者都沒有測到 Windows 和 iPhone 競寫同篇卡組 `.md`。所以我建議每次請求獨立建立一檔，手機在收到核對結果前保留本機副本。 [D-199](../../../../docs/decisions.md) · [D-201 V1–V4](../../../../docs/decisions.md) · [W1 結果](../../docs/tasks/icloud-placeholders.md)

### 替代方案與取捨

- **維持現況。** 可以維持目前的寫回界線，家長在手機上仍能複習及直接改 Obsidian 筆記。代價是手機上無法完成 AI 製卡與管理，已確認的使用情境沒有解決。
- **甲，手機與電腦直接同寫。** 手機離線也能即時操作，畫面最接近電腦。兩台本機都可能放行，D-134、D-157 和本機讀回無法保證孩子看到的每個 ID 仍連到原目標。
- **乙，手機只寫新檔、草稿或狀態。** 直接建新草稿避掉大部分同篇覆蓋，適合作為分批方向。只靠「目前沒複習紀錄」作為寫入資格，另一台可能已啟用或已收到作答。本機新建也有同名、配號及跨檔發布問題。可以先開手機準備草稿，正式提交走同一套備份與寫回。
- **丙，雙寫再加雜湊紀錄。** 可找出部分已到達的分叉，也能幫助比對與還原。紀錄晚於卡組、兩端同時離線或紀錄未上傳時，寫前仍缺對方資訊。建議把版本與操作紀錄用於單一寫入端的防重和復原。
- **備份例外，手機直接放行，或只看電腦上次成功日期。** 兩者都能少等一次電腦，但都可能允許改掉一份實際備份裡沒有的內容。單靠同一程式版號和備份時間也無法知道 ZIP 是否仍存在、是否涵蓋那份卡組。由電腦開寫入閘門比較可查證。 [D-150 的完整性與範圍](../../../../docs/decisions.md)

### 把握程度

- **高**：平台接線、本機佇列、草稿只建檔、備份在桌面端，以及現有 D-134、D-157 的偵測條件。這些可由本輪程式與決定確認。
- **中**：以配對電腦集中寫回，能降低 Cards 自己造成的競寫，同時讓家長在手機完成大部分操作。等待多久才仍值得用，以及混用、遷移、重啟、還原能否都守住，要靠試作與實機驗證。

## 第二輪：Claude 的交叉評論（2026-11-24）

**兩邊一致的**：

1. 手機預設關，每台在設定頁打開；備份與還原在手機做不到（外掛寫不到 vault 外），照舊只在電腦。

4. iPhone 實機要量：長提示與回覆的剪貼簿往返、切到 AI App 後 Obsidian 被關掉再接著貼回、iOS 中文輸入下的 ID 鎖、iCloud 兩邊改同一篇的實際結果。
5. 要新增 D-ID，修改 D-004、D-019、D-039、D-134、D-163 第 5 點、D-194，補充 D-150。

**我改變看法的**：

- **第二批照甲直接寫：撤回。** Codex 的 A／B 情境成立：D-134 的偵測要「原本的 ID 不見」和「沒見過的 ID 出現」同時成立，而且同一次載入裡有前一版可比；D-157 要兩份都讀到才擋。D-201 的 V3 實測已經看到 iCloud 對 vault 裡的一般檔「兩邊各改，只留一份、沒有副本」，分叉多半會默默收斂，D-157 接不住。我第一輪的「便宜偵測」分不出是刻意刪掉還是被蓋掉，也拿不回內容，撤回。
- **「和現在同一種風險」低估了次數。** 方向沒錯（現在手機手改筆記就可能蓋掉電腦補的 ID），但外掛在手機上主動寫（加深、加入、補 ID）比家長偶爾手改頻繁得多，而且變成兩邊都配 ID。

**我維持、和 Codex 不同的：第一批要不要也交給電腦套用。** 我認為第一批讓手機直接寫就夠安全：

1. **AI 製卡只建新檔，分叉不了。** 分叉要兩台改同一篇；建立的當下別台沒有這個檔。剩下的是跨裝置撞號，Codex 算的是每邊 100 個約 0.00113%，而且建卡組當下 `aiCreateDeck` 還會再核對一次。Codex 找到的 `writtenIn`（中斷後只看 ID 在不在就判成已寫成）也要先撞號才走得到；它值得另外修成看雜湊或寫入憑據，記成技術債，不擋第一批。
2. **啟用、暫停／恢復只改一行 `狀態`，不配新 ID。** 草稿的 ID 在存草稿時就配好，兩台的版本 ID 相同。分叉時最壞是狀態退回去（孩子暫時看不到，或暫停的又出現），或另一邊的修改被蓋掉（和現在手機手改筆記一樣），不會把作答接到別的目標。Codex 說的「啟用的是看過的那一版」：手機啟用的是手機上看到的版本；電腦剛改、還沒傳到手機的修改可能被蓋掉，這和現在手改相同，啟用的確認視窗寫出篇名與目標數讓家長核對。
3. **交給電腦套用的代價很大。** 電腦和 Obsidian 要開著，草稿才存得成、啟用才生效；要多一種在 vault 裡同步的請求檔（新格式）、配對、等待與逾時的畫面。使用者要的「不在電腦旁也能做」，第一批就變成「做到一半，等電腦」。
4. **備份閘門**（D-150 第 3 點）防的是新版寫壞已有的卡組；建新檔不碰已有內容，改一行狀態走電腦上同一條已驗過的寫入路徑。第一批不需要電腦的備份；第二批照 Codex，由通過備份閘門的電腦寫回。
5. **孩子打開開關**：直接寫時，孩子能做的（建草稿、啟用）本來就能用手改筆記做到，配對多擋不了什麼；確認視窗擋隨手點開就夠。第二批如果走「送給電腦套用」，電腦會自動套用請求，才需要配對，照 Codex。

**所以我的建議改成「乙的範圍＋Codex 的單一寫入端」**：

- **第一批，手機直接寫**：AI 製卡、啟用、暫停／恢復、入口的提醒一區（加深那一列除外）；預覽照現在的開關。規則一句話：**手機不在已有的卡組裡配新的學習目標 ID。**
- **第二批，送給一台電腦套用**（Codex 的做法）：存檔補 ID、引言框的加入、加深與加深提醒、ID 不見或重複的處理。先在試作場模擬、iPhone 實機量 iCloud；第一批用過一陣子再決定做不做：如果使用者在手機上很少需要這幾件，新格式、配對、等待的代價可能不值得。引言框的「加入」只搬已經有 ID 的候選，照理也能放第一批，但「加進已有的學習目標」會寫到別篇，Codex 列了要核對目的篇，先留第二批。

第一批要直接寫還是交給電腦，取決於使用者要不要「按下去就生效」；Codex 第一輪最後一點也點出這是會改變方案的產品資訊，所以先問使用者。使用者選直接寫，再請 Codex 跑第二輪，專找第一批直接寫的洞（站「不做」那一方），之後才寫 D-ID；選等電腦，就照 Codex 的方案，兩邊已一致。

Claude 的初步看法（已回覆使用者，待 Codex 第二輪一起查）：

- **鑰匙**（近似丙）：鑰匙和卡組都經 iCloud，沒收到新鑰匙分不出「沒改」與「改了還沒到」，當不了真正的鎖。做得到的是：動手前，鑰匙到了而卡組沒到或內容對不上就先停；另一台很久沒回報時警示；事後兩台的鑰匙都到了就抓得到「從同一版各改一次」，提醒家長，不再默默只留一份。真正的鎖要一台兩邊隨時連得到的伺服器當裁判，入口網站（`apps/Portal`，Cloudflare）做好後才有條件。
- **自己修好**：前提是被蓋掉的那一份還留著，所以和鑰匙一起做：外掛每次改卡組，改之前、改之後各留一份（同 AI 製卡快照的做法）。修法多半是機械的：把不見的學習目標連同原本的 ID 放回去，作答照 `lt` 自動接回。由外掛做、家長確認；AI 只在兩邊改了同一行時提建議，不決定 ID 屬於哪個目標（D-134 不猜身分）；修之前先留快照。直連 AI 暫停中，修理先不靠 API。
- **放在第二批**：第一批（AI 製卡、草稿啟用）用不到；第二批可以用「留證據、事後修」（丁′）取代 Codex 的「等電腦套用」，電腦關著也能立刻生效；代價是 `紀錄/` 多一種檔案格式、要格式查核與第 1 類測試。

**先跑單元測試與試作場。** 用兩個獨立的本機視圖加一個孩子讀端控制事件順序。用合成卡組及固定 ID、雜湊、作答行當預期值。第一批有以下放行條件，均待驗證。

| **建檔與中斷，第 1 類** | 強制兩端選同名及撞 ID，分別在原文、草稿、快照和清理前後中斷。涵蓋 `started` 異文同 ID、改名到他檔、逾時後晚到、清掉本機工作後重試。重跑同一次操作最多一份有效結果，原檔零覆蓋，錯的篇不進快照，半成品在任何 Cards 入口都不出題。 |

### 3. 第二批的條件

- **裁判要能原子地比對版本與發鑰匙。** 每個 vault 的每篇卡組需要跨裝置穩定的身分，改名仍是同一篇。伺服端核對預期版本與雜湊，同一版本只核發一個有效寫入權，並用單調遞增的憑據拒絕過期持有者。重試要能辨認同一操作。引言框「加入」若碰兩篇，兩個對象都要受保護，並規定只寫成一篇時怎麼復原。Durable Objects 的強一致交易儲存可以實作這一段。Portal 有 Cloudflare 頁面即可部署，待開工驗證的依賴是協調和授權能力。 [Cloudflare Durable Objects 儲存文件](https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/) · [Portal 儲存與版本介面](<../../../../apps/Portal/docs/Claude Codex Discussion/2026-11-20-portal.md>)
- **鑰匙、檔案落盤與孩子採用的版本要接在一起。** 拿鑰匙後在實際寫入回呼重讀比對本機全文。iCloud 若先送來舊版或其他內容，立即拒寫。寫完讀回後才提交成功。若舊版在讀回之後抵達，讀端也要核對已確認的版本與雜湊，遇到異文就停受影響的目標並保留紀錄。如果仍以原 `.md` 路徑作為所有裝置直接採用的來源，Cloudflare 無法回收 iCloud 上已送出的舊寫入。要把鑰匙當成版本保證，須證明讀端只採用可驗證的已提交內容，且相應全文找得回來。例如伺服器確認唯一版本與雜湊，內容以不可覆蓋的版本檔保存在使用者的儲存端。單次寫入的本機讀回不足以驗證這條保證。 [現有 iCloud 實測](../../docs/tasks/settings-vault-file.md) · [Apple iCloud 檔案協調說明](https://developer.apple.com/documentation/technologyoverviews/shared-data)
- **所有 Cards 改既有卡組的出口都要參與。** 包括電腦、手機、第一批的啟用、補 ID、加入、加深、狀態變更與還原。舊版仍能寫時，不能把同一篇視為受保護。Obsidian 手編、其他外掛或外部編輯器要有導入與重新核對流程，讀到未核可內容時不能默默當成已提交版本。手機或電腦離線、Cloudflare 連不上、租約到期或前次結果不明時，只允許準備本機工作，不改正式篇。重連先核對前次結果，不自動重送。只有一台裝置也適用同一條規則，因為還有還原、晚到同步和重新安裝。離線孩子可繼續使用上次已驗證且可用的資料，無法即時收到新撤回。 [D-036](../../../../docs/decisions.md#d-036-直接在-obsidian-編輯卡組) · [D-149](../../../../docs/decisions.md#d-149-更新與相容版本紀錄讀取閘門與正式安裝) · [現行還原與寫入閘門](../../src/state/writes.ts)

- **改前改後各存可讀回的完整版本。** 建議設專用的還原資料區，在 vault 裡要證明不會被辨識為卡組或作答紀錄，且要說清楚共享成員能讀到什麼。每份以獨立檔案保存，改前副本先持久化並驗雜湊，改後全文與提交版本對上才算完成。納入電腦的 D-150 獨立備份。**試作期間先不自動清理。** 正式保留期至少涵蓋一個月備份週期與量到的最長離線／同步延遲。即使到期，未結案、可能仍有晚到作答、或沒有獨立且驗過可還原的副本，就繼續保留。vault 內副本能修個別改寫，同一個 vault 整體受損仍要靠獨立備份。 [D-150 第 4～8 點](../../../../docs/decisions.md#d-150-備份與還原) · [卡組路徑判斷](../../src/core/deck/read.ts)

### 把握程度

- **高**：現行確認只傳路徑、啟用可能同時補最低版本、發布順序先草稿後快照、本機的 ID 與備份閘門看不到尚未同步的資料，以及 `writtenIn` 對 `started`／`written` 的異文判定。前幾項有程式碼依據，最後一項另有唯讀探針。

## 第三輪：Claude 對 Codex 第二輪的回應（2026-11-24）

**照單全收的**（第一批一起做；1～3 在電腦上現在就有，修在同一條啟用路徑上）：

1. **`writtenIn`**：第一批開放前修好。中斷後用發布代號和內容雜湊核對是不是這次寫的；認不出來就停在衝突畫面、保留工作，不自動重建、不自動發布。
2. **半成品先被啟用**：啟用的共用門檻先核對這次發布已經完成（快照在、而且列了這一篇），電腦和手機都一樣。
3. **確認 A、寫入 B**，以及「沒有改」被說成「已啟用」：確認綁定那一版的內容雜湊，寫入當下再核對；結果分成這台寫成、早就啟用了、內容變了、結果待確認。
4. **兩台各建同名新檔**：原文與快照的檔名帶發布代號（使用者很少打開）。卡組的檔名怎麼避開寫任務時定；如果會讓篇名多出看得到的短碼，先問使用者。
5. **跨裝置撞號**：不做分區開頭，照實寫進 D-ID 的限制：只在同步空窗裡兩台各自配號時才會撞，每邊 100 個約 0.00113%；[D-157](../../../../docs/decisions.md#d-157-重複的學習目標-id先停家長選) 只在兩份都讀到時擋。
6. **待貼回的工作只在這台手機**：畫面寫明工作只存在這台、什麼時候到期；每一步讀回才說已存；本機的工作不見了不自動重發、不重配 ID。
7. **孩子打開開關**：照使用者定的「預設關、設定頁打開、打開時確認」，目標是防誤開，不做獨立的家長授權；寫入那一層再查一次開關，關掉後已開的視窗失效。
8. **混版**：手機只拿到兩個窄的寫入權（AI 製卡建新檔、啟用），不把 `fillIds` 整個打開；新格式先發讀得懂的版本，舊版最壞是看不到，不能讀錯。

**要改做法的：手機的「啟用」不改卡組，改成另建一筆「啟用紀錄」**

Codex 最大的洞（手機啟用本機的舊草稿，蓋掉電腦改過、孩子已經練過的新版），還有「確認 A、寫入 B」「沒網路」「又變回草稿的提醒會誤報」，都來自同一件事：手機改了一個已經存在、別台也可能在改的檔。Codex 的解法是收窄（手機只啟用自己建、沒被改過的草稿），但它也指出還要證明其他寫入端在這段期間不會接手改寫，否則擋不住；那就得再限制電腦不能改手機建的草稿。

提案：手機按「啟用」時不動卡組，另外建一個新的小檔，記家長確認的是哪一版（那一篇當下全文的雜湊、時間、操作代號）。

- 讀卡組的每台裝置（家長手機、孩子手機、電腦）看到一篇草稿的全文雜湊等於某一筆啟用紀錄，就當成已啟用：立刻生效，不用等電腦。
- 電腦下次開著時把它收進卡組：走現在電腦的啟用寫入（過備份閘門），寫入當下再核對雜湊，之後刪掉那筆紀錄。
- 這中間卡組被任何一台改過，雜湊對不上，就維持草稿，孩子不會看到沒審過的版本；手機和電腦都提醒家長「手機啟用的那一版已經改過，要再看一次嗎」。

和收窄比：

- 第一批手機不改任何已經存在的檔，「蓋掉別台的版本」整類不會發生；不需要啟用前留全文、不用判斷有沒有網路、不需要「又變回草稿」的提醒（換成雜湊對不上的提醒，這個判斷不會誤報）。
- 確認 A、寫入 B 自然解掉：紀錄記的就是家長看到的那一版。
- 手機可以啟用電腦做的草稿（收窄做法不行），在手機上審電腦做的卡更順。
- 舊版外掛不讀這種新檔，看到的仍是草稿：混版時最壞是孩子晚一點看到。
- [D-150](../../../../docs/decisions.md#d-150-備份與還原)：手機只建新檔，不需要備份閘門的例外。

代價與要先想清楚的：

- 新的檔案格式（放哪、長什麼樣，寫進 `syntax.md`），三個讀的地方都要認得；雜湊要跨平台一致（換行、BOM）。
- 電腦要做收進與清理；電腦一直沒開時紀錄留著，不影響使用。
- 刻意退回草稿之後，舊的啟用紀錄不能再把它啟用（例如只認比那一篇最後一次狀態變更晚的紀錄）。
- 手機啟用後又手改那一篇（現在本來就可以手改），雜湊變了會回到草稿，要提醒家長再按一次。

第二批的暫停／恢復也許能用同一招、不必等 Cloudflare；第二批開工時再評估，不改使用者已定的方向。

Codex 列的第二批條件照錄，開工時當檢查清單；D-ID 照 Codex 的分法（第一批現在寫、第二批只寫方向），等這一輪查完、雙方一致再寫。
