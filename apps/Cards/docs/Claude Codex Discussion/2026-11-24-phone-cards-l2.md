## 發現

### R1 · P1　電腦啟用可能把同步進來的新版改回舊文

**規格｜已重現至 Obsidian 替身與 state 公開介面。** 預期在寫入當下核對家長確認的版本，回 `changed` 或 `already` 時零寫入。實際上，`activateDeck` 在排隊前核對一次磁碟。輪到寫入時，`changeStatus` 用編輯器文字比對，且回傳 `null` 拒絕時，`writes.edit` 仍會呼叫 `persist()`。

- **證據一。** 讓一筆建檔占住佇列，從 `activateDeck` 發出啟用，等它通過排隊前的核對，再改編輯器文字。結果提示「還沒啟用」，但 `view.save()` 被呼叫 **1 次**。用 `state.activateDraft` 測 `already` 也呼叫了儲存。
- **證據二。** 將磁碟答案從「你好」改成「您好」並送出變更通知，保留編輯器中的舊文。`state.activateDraft` 回 `done`，測試的持久化出口把磁碟寫回「你好」，並將草稿設為啟用。

**實際路徑與機率。** 電腦正常的編輯模式會走這條路。拒絕後呼叫儲存只需要內容在排隊期間改變。覆蓋還要求同步先改了磁碟、編輯器仍持有舊版，且宿主接受儲存，預估低頻。實機是否會在這個時間窗保留舊編輯器並落盤，待驗證。**合併前修**，讓拒絕直接結束，並把磁碟與編輯器的核對放進寫入佇列。

### P1｜延續 R1　磁碟變更通知晚到時，啟用仍會覆寫新版

**規格｜已在 state 公開介面重現，Obsidian 實機時序待驗證。** 探針讓一筆建檔占住寫入佇列，確認時編輯器、磁碟與索引都是 A。啟用排隊後把磁碟換成 B，保留編輯器中的 A。先送變更通知時，結果是 `changed`、`persist()` 0 次、磁碟保留 B。把通知延到啟用之後，結果是 `done`、`persist()` 1 次、磁碟被寫回 A，並標成啟用。

## 核對與測試結果

- **狀態寫回。** 正常啟用、暫停、恢復都可寫入。草稿按暫停回 `unchanged`，`persist()` 0 次。剛建好的草稿若還沒進索引，首次回 `changed`，寫入出口隨即安排重讀。同一探針未送建立通知，重讀後再啟用仍回 `done`。
- **閘門與索引。** `writeBlock(true)` 的順序是手機開關關閉、載入中、已關閉、還原或還原卡住、備份、讀不到。手機開關開啟後仍遵守後續門檻，手機的一般寫入閘門仍回 `phone`。`aiWhere([])` 在已載入且可讀時回空 `Map`，手機開關關閉或電腦備份未完成時也可能如此。載入未完成或卡組讀不到時回 `null`。首次儲存會再查寫入門檻，但還原期間的等待有上述回歸。
- **一般快照連結與檔名。** 完整路徑可區分可見的同名卡組，普通路徑的卡組改名與搬移可由 `retargetSnapshot` 更新。`v0.6.0` 的讀取程式已支援含 `.md` 的完整路徑與別名。D-227 明文收窄 D-226 第 5 點，並補充 D-081。`syntax.md` §0、§6 的手機檔名、電腦沿用原名與可見撞名規則一致。程式的兩支手機隨機識別碼空間為 `23 × 31⁵ = 658,470,473`，符合文件的約 6.6 億分之一。
- **本機驗證。** Windows、Node 24.13.0，與指定差異相關的 9 個測試檔共 **131 項通過、0 項失敗**。文件檢查與 `git diff --check` 通過。完整 `npm run check` 依送審資料由雲端 pre-commit 跑過，本輪依 L2 沙箱規則跑相關測試。

**待驗證**：Obsidian 開啟「自動更新內部連結」時，這批新製卡快照在改名、搬移後的實際連結格式與事件順序。本機宿主封裝讀取遭沙箱拒絕，repo 既有 Windows 證據涵蓋加深快照的外掛更新及「僅此一次」，本輪未重跑宿主。電腦啟用的同步通知窗口、iPhone 實機流程與兩台 iCloud 實際同步也待驗證。
