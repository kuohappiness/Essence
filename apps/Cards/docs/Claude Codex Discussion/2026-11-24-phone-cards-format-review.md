### 3. §3-1 要定出能驗證的 JSON 契約

**看規格推斷；真實路徑是同步未完成、還原後、退版或同時建立紀錄。** 草案列了欄位，缺少型別、必要欄位和相容規則。建議 v1 使用英文 JSON 鍵，沿用設定、複習紀錄與考試切面的慣例。必要欄位用 `v: 1`、`path`、`sha256`、`need`。`path` 是 vault 相對的實際卡組路徑，含 `.md`，按完整路徑比對。拒絕絕對路徑、反斜線、空路徑段及 `.`、`..`，禁止退回用同名搜尋。`sha256` 為 64 個小寫十六進位字元。`need` 為合法正式版號字串或明寫 `null`。

操作代號可由檔名提供，省掉 JSON 裡重複的 `id`。啟用紀錄的代號沒有出現在卡組篇名裡，可以用高熵、檔名安全的代號。重試沿用代號，本機建立要有只建新檔的保護，同路徑同內容可確認完成，異文留原檔。`t`、`device` 若保留，可沿用複習紀錄的格式作診斷，兩者都不參與啟用、身分判斷或排序。

讀壞 JSON、空檔、NUL、必要欄位缺漏或型別錯、`v` 未知、`need` 無效或太新，都使**該筆**無效。未知附加欄位可以忽略，新增會改變啟用語意的欄位要升 `v`。同一篇有任一筆有效且吻合的紀錄即可啟用。壞檔的 `path` 未必取得到，診斷只能指到紀錄檔本身，毋須推測它屬於哪篇。同步衝突副本的檔名是否可讀也要定下來，至少要有異文副本的拒絕測試。這是新增格式的必要契約，應先定文字與輸入輸出範例。  
證據：`phone-cards.md:67–81`、`syntax.md:53–61,717–731,753–769,924–948`、D-149 第 3 點、D-226 第 2、4 點。

### 4. 雜湊和最低版本要從同一份磁碟原文判定

**已重現兩版的解析和版本行為。** 用一份有實際卡題及 `^abc234` 的草稿測試，檔首單個 BOM、CRLF、單獨 CR 與 LF 在提案正規化後雜湊相同，解析結果也相同。刪除尾端 LF 後雜湊不同，但該例卡組解析與題目指紋相同。把 `café` 改成 NFD，雜湊和這個例子的題目指紋都變了。`parseDeck` 的 `linesOf` 認三種換行，`tracker` 則保留採用的原文；現有電腦確認只正規化換行。

規格應明定「去掉一個檔首 BOM，將 `\r\n` 與 `\r` 換為 `\n`，其餘字元逐一保留，再用 UTF-8 算 SHA-256」。預覽、建紀錄前核對、採用及電腦接手都用這個定義。單純 CRLF 轉 LF 不會使紀錄失效。只開檔而沒有改寫位元組也不會失效。若 Obsidian 開關檔會改尾端換行或正規化 Unicode，就會退回草稿。**Obsidian 自動存檔與 iCloud 真實行為待驗證**。維持全文比對可保住核准的內容邊界，沒有證據前不宜把尾端或 Unicode 的差異納入等同規則。

`withNeed().need` 不能當格式欄位的來源。兩版均重現：

- 普通草稿已有 `需要版本: 0.6.0`，`withNeed` 仍回 `need: null`。
- 有比較卡且屬性可寫時，回 `0.4.0`，`markOf` 為 `missing`。
- 同樣的比較卡使用單行 `{狀態: 草稿}` 時，`markOf` 為 `refused`，`withNeed` 又回 `null`。
- 以 `0.3.0` 的讀取能力跑 `withNeed` 時，也可能因內容檢查被版本條件跳過而回 `null`。

較簡化的寫法是讓**內容最低版**有一個共用的純判定，沿用比較卡、`pick-answer-invalid` 和正式目標含 `課外：` 的規則。先驗原有標記，再用 `laterRelease` 取原標記與內容最低版較新的值。遇到標記壞掉、這台版本太舊、新版號不明或需要的標記加不上時，拒絕建立紀錄。保留「試加」時只在記憶體驗證，手機不寫 Markdown。新版讀取時仍以卡組原有的版本閘門為先，並檢查紀錄的 `v`、`need`，以及 `need` 是否低報這份卡組的最低版本。`0.6.0` 忽略 JSON，沿用 Markdown 的草稿狀態與原有標記。電腦真的寫成 `啟用` 時，所需的 Markdown 版本標記必須在同一次備份保護下寫入。  
證據：`src/core/deck/markdown.ts:16–18`、`src/core/deck/parse.ts:48–50,113–118,140–141`、`src/state/index.ts:819–839,908,923–935`、`src/state/need.ts:12–39`、`src/core/deck/need.ts:37–68`、`src/core/version/release.ts:7–43`。

### 5. §3-2 與 §3-4 要寫清楚有效狀態的來源及電腦寫回的最後核對

**看規格推斷；正常編輯、同步和電腦存檔都能走到。** 如果裝置採用 A 的啟用紀錄後，已在磁碟收到 B，電腦存檔若用快取的「有效啟用」去寫 B，就會把未核准的 B 寫成實體 `啟用`。現行讀取會保留新原文，但解析結果相同時可能略過重建。若僅改 `planList`，目前從 `deckList` 讀的狀態觀察、AI 已有目標、英文已有單字與「同單元已經有」也會和排程分歧。

任務應要求同一份採用的原文決定有效狀態，讓觀察、排程、目錄及 AI 的消費端都讀到。啟用紀錄新增、消失、失效、晚到，或卡組全文變動，即使解析結果相同，也要重算受影響的卡組。電腦接手須在正常寫入的回呼中，**用該次實際要修改的底稿**核對啟用紀錄，再把狀態、ID 或 `需要版本` 一起寫回。B 對不上 A 時，不得沿用 A 的啟用。暫停要落成實體 `暫停`。手機建紀錄後也要以本機已採用且吻合的狀態，才顯示「這台已啟用」。

§3-2 的「其他：草稿」應限定在明寫 `草稿` 的分支。兩版均重現無 `狀態` 的手寫卡組預設啟用，無效的狀態值也走既有預設並提示。這是 D-081／syntax §2-1 的舊行為。若要讓家長手動刪除 `狀態` 或寫壞屬性時也一律停出題，須另定相容行為。D-134 的例外仍只限手機建新草稿時配 ID，啟用紀錄與狀態投影不授權補 ID。

### 6. 啟動、回測與重啟用提醒需要明確的預期

**看規格推斷；晚到、逾時及再次啟用都是真實路徑。** §3-2 同時要求啟動先讀完才觀察，以及讀不到可先維持草稿。若第一輪逾時就把先前已觀察的 `啟用` 寫成 `草稿`，同一筆紀錄晚到後又會寫 `啟用`，重開可反覆發生。建議規格區分「已確認不吻合」和「初次清單或已知紀錄還沒讀完」。後者逾時後可讓其他卡組照常工作，暫不為受影響卡組寫草稿觀察，讀取結束後重新比對。真正的內容或路徑不吻合才依有效狀態記錄。§3-5 也應以**目前草稿沒有任何吻合紀錄**為提醒前提。A 的舊紀錄在 B 已核准後仍會存在，若逐筆報異文，家長已重啟用還會一直收到提醒。

**syntax §5-4 的切面原文及收錄條件可保留。** 兩版都從 `tracker` 取卡組原文，且按範圍收錄草稿、暫停等狀態。回測應使用同一裝置的 `set: status` 觀察判斷當時的有效狀態，保留切面的原始 `草稿` 字樣。觀察與切面之間證據不足時，結果應標未知。新版觀察到 `啟用`、舊版觀察到 `草稿` 是可預期的混版結果；電腦把同一版接寫成實體 `啟用`，已觀察過有效啟用的同一台不多記一次。  
證據：`phone-cards.md:77–81,94–108`、`src/state/index.ts:537–565,712–724,843–889`、`src/state/observe.ts:19–53`、`syntax.md:678,747–777`。
