- **要求的正本**：寫說明書時要寫什麼，原本散在 D-048 的 17 段補充與其他決定；第 3 節的章節表把它們收成一張表並標出來源。來源的全文仍以決定為準，這裡不重抄。

## 1. 為什麼現在規畫（和不做比，D-153）

不做＝照舊把要求累積在 D-048 的補充，v1 最後一次寫完。

1. **要求散在很多地方，有些已經被推翻**：D-048 有 17 段補充，其中三處後來改掉（「開始複習」改成一科一列、「只做某單元今天的卡」拿掉又恢復、深度三層改成不設頂）；另外約 12 條決定各指定一兩句（D-070、D-079、D-097、D-107、D-125、D-126、D-149、D-154、D-155、D-157、D-160、D-198），Cards 的 backlog 有 4 項、roadmap〈等觸發點〉有 2 列、plans 有 3 處。最後才整理，容易漏、也容易照著舊說法寫。收成一張章節表後，之後每個新要求直接寫進對應的章。
2. **外掛裡有幾個地方要連到說明書的某一節，現在沒有網址可以連**：設定頁連到「怎麼申請 API 金鑰」（D-048 2026-10-11 補充）、提醒一區與存檔受阻的提示連到「有檔案暫時讀不到」（D-154）。每一節的固定網址要先定，這些功能才收得了尾。
3. **形式會影響之後每一個任務怎麼留資料**：例如截圖要用示範用的 vault、不能拍到課本內容（D-003）與孩子的真實紀錄。先定下來，之後做功能時順手準備，不用最後重來。

代價：這一串的幾輪討論、一份規畫文件；之後多維護一張章節表（取代繼續往 D-048 加補充，沒有多一份）。

## 2. 讀者與寫法

**誰會讀、在哪裡讀**

| 讀者 | 要做的事 | 在哪裡讀 |
|---|---|---|
| 製卡與管理的人（多半是家長，也可能是自己用的學生或大人） | 安裝、製卡、審核、設定、備份、更新、排解 | 電腦，邊看邊做 |
| 每天複習的人（多半是孩子） | 怎麼複習、怎麼自評 | 手機，幾乎不讀；一頁、以圖為主 |
| 接手的人或 AI、想知道設計理由的人 | 附錄「規劃過程」 | 電腦 |

**寫法**（前五點已有決定或使用者的話，這裡只是集中）

1. **從情境出發**：先寫「想做什麼 → 去哪裡按」，再說明背後的規則（D-048 2026-10-17 補充）。
2. **不期待有人從頭讀到尾**：使用者在 [D-169](../../../../docs/decisions.md#d-169-家長亂填出處是常態程式不猜看不懂就當場教) 說過「寫了也不會有多少家長讀」。畫面上當下說得清楚的，不靠說明書；說明書是拿來查的，外掛裡的連結直接到那一節。
3. **把讀者當成不熟悉電腦的人**（使用者 2026-11-07）：不要求 Git、命令列、改 JSON；一步一張圖。
4. **沒做完的不寫成可以用，沒走過一次的流程不寫**（AGENTS.md 底線、[D-198](../../../../docs/decisions.md#d-198-只做軟體不限制使用方式)）；學習效果寫成待驗證的目標。
5. **只寫軟體怎麼用**：不寫教家長怎麼教孩子的建議（使用者 2026-11-03）；「讓系統判斷得準」那三條是軟體的用法，照寫。
6. **會過期的內容標查核日期**：API 金鑰來源、iOS 的操作步驟、語音下載；每次發布新版前重查（D-048 2026-10-11 補充）。
7. **用詞照畫面上的字**：入口、目錄、當日卡、全部卡、提醒、學習目標、題目池、卡組；一個東西只有一個名字，附一頁名詞表。

## 4. 樣式

### 4-1 形式：Markdown 當正本，自動產生網站

- **正本是 repo 裡的 Markdown**，一節一個檔；合併進 `main` 時由 GitHub Actions 產生網站、發布到 GitHub Pages（和進度白板同一條路）。D-048 寫的「HTML 格式」是產出的結果。
- **為什麼不是手寫一個 HTML 檔**：三四十節加幾十張圖放在一頁，手機開很慢；AI 改 HTML 的差異難審；文件檢查（壞掉的連結）用不上。
- **為什麼不放進 vault 當筆記**：圖片會讓 vault 變大、拖慢 iCloud 同步；每次改版要同步到每一台。
- **用現成的文件網站工具**（例如 VitePress），不自己寫產生器：側欄、搜尋、手機版面都現成。用哪一個，開工時拿一頁實際試中文搜尋與手機版面再定。
- **每一節有固定的網址**（英文短名，例如 `/troubleshoot/files-unreadable`），定了就不改；外掛裡的連結集中在一張表，網站之後搬到入口網站的網域時只改一處。
- 正本放哪個資料夾，照 [architecture.md〈repo 結構〉](../../../../docs/architecture.md#9-repo-結構-d-208)在開工時定。三個軟體的說明書分開寫（D-219）；三份要不要放在同一個網站、用同一套樣式還沒定，談形式那一題時一起問。

### 4-2 一頁長什麼樣子

情境頁固定四段：

1. **標題是想做的事**：例如「只想練某個單元」，不是「目錄畫面說明」。
2. **步驟**：編號，一步一句、一張圖；圖上只標這一步要按的地方。
3. **背後的規則**：預設收合，想知道的人再打開（例如單元數字的顏色怎麼算）。
4. **相關的節**：最多三個連結。

概念頁（第五部）：先一句話的結論，再一個真實例子（聲音單元、溶質與溶劑），最後才是設計理由。

### 4-3 視覺

- **延續複習畫面的安靜樣式**（[D-070](../../../../docs/decisions.md#d-070-複習畫面採用安靜樣式)）：白底、留白、系統黑體（D-180）；顏色只用在有意思的地方：記憶配色（D-062）和畫面上一樣，提示框只有三種（不能做的事、要注意、小提示）。
- **截圖**：電腦的統一寬度；iPhone 的放進手機外框、統一大小；深色與淺色只拍淺色。
- **示範用的 vault**：截圖一律在示範用的 vault 拍，卡組用自己寫的內容（例如聲音單元），不拍到出版社的課本（D-003）、孩子的姓名與真實紀錄。
- **圖**：首頁的循環圖與「整個複習流程」的流程圖畫成 SVG，手機上清楚；附錄的流程圖沿用 repo 現有的 mermaid。
- **首頁用循環圖當地圖**：每一站點進對應的章。這是「說明書用心智圖展開」（[experience.md](experience.md#其他待評估的操作與呈現)，💬）的小做法；完整的心智圖版等 Mindboard。
- **每頁頁尾**：適用的外掛版本、最後查核日期。
- **外掛自己的畫面可以由程式拍**（2026-11-22 試做時驗證，見第 5 節〈試做的結果〉）：入口與複習畫面不用等 Cards 網頁版的建置，現在就能用腳本拍，還能自動標出要按哪裡。Obsidian 的工具列與設定頁、iPhone 的系統畫面拍不到，仍要手動拍。

### 4-4 樣式怎麼挑

照之前挑複習畫面的做法：做兩頁真的內容當樣式稿，一頁情境頁（「今天的複習」，功能已在正式 vault 用了幾版）、一頁概念頁（「學習目標 ID 與題目指紋」），各出兩三種版面，使用者在電腦和手機上看過再選。

## 5. 什麼時候開始

**建議分四段，不是「現在全寫」，也不是「最後才開始」。**

| 段 | 什麼時候 | 做什麼 | 產出 |
|---|---|---|---|
| A 定骨架 | 現在（這一串） | 確認讀者、形式、章節表 | 這份規畫談定的部分 |
| B 外殼與樣式稿 | A 談定後，v1 的空檔，一件小任務 | 網站外殼、發布流程、每一節的固定網址、兩頁樣式稿 | 使用者挑定樣式；外掛裡的連結有地方連 |
| C 收要點 | v1 進行中，一直到正文開工 | 每個功能任務合併時，在章節表對應的章補「要寫的」一兩句；不寫正文 | 章節表保持最新 |
| D 寫正文 | 觸發點見下 | 先寫不靠截圖的（第五部、資料夾、不能做的事）→ 各情境章 → 安裝、更新、兩台裝置（最後）→ 附錄；截圖集中一次拍，iPhone 的和最後一次 iPhone 實機測試排在同一次 | 完整的說明書 |
| E 驗證 | 正文寫完 | AI 當沒看過 repo 的讀者，照說明書在測試用的 vault 從安裝走到第一次複習；再請一位沒用過的人照「快速開始」走一次 | v1 驗收的說明書那一項 |

**D 的觸發點**：v1 的功能任務都合併、最後一版裝到正式使用的 vault、之後沒有排定會改畫面的任務。

**為什麼正文不現在寫**

- v1 還有 20 項功能沒開工、13 項做了一部分，其中錯題補強、加深、考前抽測、提醒一區、調整製卡規則都是說明書的大章；入口與目錄的第三批還沒決定。現在寫的截圖和步驟，之後多半要重拍、重寫。
- 現在的使用者只有自己家，正文早寫出來沒有人讀；真正需要的時間點是給其他家庭之前，以及 v1 驗收。
- 安裝、更新、兩台裝置這三章受[入口網站與網頁版](<../../../Portal/docs/Claude Codex Discussion/2026-11-20-portal.md>)影響最大：孩子改在網頁複習的話，iPhone 那一半（保持下載、語音、換新版）會大改，所以排在最後。

**為什麼骨架和外殼不等到最後**：第 1 節的三點。B 是小任務（外殼、發布、兩頁），不靠還沒做的功能。

**更小的做法**：只做 A 與 C（一張章節表），B 也延到正文開工時。差別是外掛裡要連到說明書的地方在那之前沒有網址可連（先連到 repo 的文件或不放連結），樣式到最後才挑。如果 v1 剩下的任務裡沒有要連到說明書的，選這個也可以。

### 試做一節完整版

使用者 2026-11-22 同意分段照上表：先做骨架與樣式稿（A、B），正文等功能都合併才寫。同一則訊息提出：先挑一節以後比較不會變動的，試做完整版看看，並問「如何安裝外掛到 Obsidian」適不適合。

💡 Claude 的看法：試做一節完整版值得做，它就是 B 的樣式稿做到完整（真的步驟、真的截圖、背後的規則都寫完），比只看版面更能判斷寫法與維護的代價。但「安裝」不適合當第一節，它是章節表裡最會變的一節：

- **給一般家庭的安裝管道還沒做**：現在正式使用的 vault 是維護的 AI 在電腦上用安裝命令裝的（D-149 第 4 點）；GitHub Release、BRAT、上架社群外掛排在第二階段、給其他家庭之前（[updates.md](updates.md#實作順序) 第 6 點）。現在寫，寫的是沒有人走過的步驟（AGENTS.md 底線：沒走過一次的流程不寫成可以用），管道定了還要重寫。
- **iPhone 那一半受網頁版影響**：孩子改在網頁複習的話，iPhone 不用裝 Obsidian 與外掛。
- **「讓 vault 一直留在裝置」的 iPhone 做法還沒查清楚**：iOS 27 找不到「保持下載」（[backlog 技術債](../backlog.md#技術債)）。

比較合適的候選：

| 候選 | 為什麼穩定 | 試得出什麼 |
|---|---|---|
| 「今天的複習」（入口的科目列 → 翻面 → 四個自評按鈕 → 做完） | 從 `0.1.0` 用到 `0.6.0`，畫面照 D-070、D-096 定案；入口與目錄還沒定的第三批是管理模式，不動這條流程 | 情境頁的完整寫法：步驟、手機截圖、背後的規則、給複習的人看的那一頁 |
| 「學習目標 ID 與題目指紋」 | ID 的格式與指紋的算法列在「永遠不改」（D-149 第 3 點） | 概念頁的完整寫法：結論、例子、設計理由；不用截圖 |
| 「資料夾管理規範」與「不能做的事」 | 系統資料夾的規則已定、防呆已上線（`0.4.0`） | 規則類的頁面與警告框；截圖很少 |

💡 建議先做「今天的複習」；要兩頁就加「學習目標 ID 與題目指紋」，剛好是 4-4 原本要做的兩頁樣式稿。「安裝」等發布管道做出來、實際走過一次再寫。

### 試做的結果

使用者 2026-11-22 選「今天的複習」。試做稿在專案檔案 `使用說明書/今天的複習樣式稿/`（還沒進 repo），是整節寫完的情境頁：六個步驟、四個按鈕怎麼選、四個可能遇到的情況、七條背後的規則、三個相關的節。同一份內容做成三種版面。**使用者 2026-11-22 選：電腦用 B、手機用 A**（跟著螢幕寬度自動切換，分界先用 600 像素）：

| 版面 | 排法 | 手機上整頁的長度（約） |
|---|---|---|
| A 一步一圖 | 每一步文字在上、大圖在下，由上往下讀 | 6,800 像素 |
| B 圖文並排 | 字在左、圖在右；手機上圖縮成小圖，點一下放大 | 4,200 像素 |
| C 左右滑 | 步驟排成一排卡片，左右滑著看；後面的步驟要滑才看得到 | 3,900 像素 |

試做時發現的：

1. **截圖可以用程式拍**。外掛的入口與複習畫面（`src/ui` 的 `openEntry`、`openReview` 加 `src/state`）不靠 Obsidian 就能在瀏覽器裡跑：把 `obsidian` 模組換成替身、檔案放在記憶體，用 Playwright 照劇本操作並截圖。21 張大約 1 分鐘，還能記下每一步要按的按鈕在哪裡，自動畫出標示。試作在專案檔案 `使用說明書/截圖工具/`。
2. **拍不到的**：Obsidian 自己的畫面（工具列、設定頁、命令面板）和 iPhone 的系統畫面。所以安裝、更新、兩台裝置、設定那幾節仍要手動拍。
3. **和實機不完全一樣的**：Markdown 的渲染是簡化的替身，字型是 Noto Sans TC（iPhone 上是蘋方）。正式採用前要拿幾張和 iPhone 實機的畫面對一次。
4. **示範用的卡組要夠多**：試作只有 9 張，入口每一科都顯示「1 分鐘」；正式的示範 vault 每科要有二三十張，時間與進度才像真的。
5. **每一條規則都要對過程式或決定才寫**：這一節對了 D-062、D-069、D-070、D-084、D-095、D-096、D-120、D-160 與 `Review.tsx`。
6. **這一稿先做的假設（還沒談）**：對複習的人說「你」（第 6 節第 2 題）；「相關的節」指向的三頁還沒寫。

接著做 4-4 的另一頁樣式稿（概念頁「學習目標 ID 與題目指紋」），屬於使用者同意的「先做骨架與樣式稿」。💡 還沒同意的：把截圖工具搬進 repo、改成相對路徑，當成說明書建置的一部分。

### 寫完之後怎麼跟著功能更新

使用者 2026-11-22 問：說明書會不會跟著功能自動更新、維護代價大不大。不會完全自動；目標是使用者幾乎不用管。

| 哪一塊 | 誰做 | 做法 | 代價 |
|---|---|---|---|
| 發布 | 自動 | 正本合併進 `main`，網站自己重新產生 | 無 |
| 文字 | 做功能的 AI | 「改到的說明書那幾節」寫進功能任務的完成條件，同一個 PR 一起改 | 每個任務一到三節、每節幾段 |
| 不漏改 | 機械檢查 | ① 一張「程式的哪一區對應說明書哪幾節」的表，PR 改了那一區卻沒動說明書就提醒（可以寫一句「說明書不用改」放行）；② 說明書裡寫到的按鈕與畫面名稱，在程式的字串裡要找得到。兩個都接在現有的文件檢查 | 兩個小工具與它們的測試；表要跟著章節維護 |
| 截圖 | 使用者（iPhone）、AI（電腦） | 會常改的畫面少放圖；發布前由工具列出這一版要重拍的圖，和上線前的 iPhone 實機測試排同一次；外掛自己的畫面（入口、複習）可以由腳本重拍（〈試做的結果〉第 1 點），手動的只剩 Obsidian 與 iPhone 系統的畫面 | 原本是維護的主要代價；腳本能拍的部分降到跑一次腳本 |
| 會自己過期的 | AI，每次發布前 | API 金鑰來源、iOS 步驟、語音下載照查核日期重查；要實機的併進 iPhone 測試 | 每版一次 |

- **和不做比**：不設這些機制，說明書會在幾版之內和畫面對不上；對不上的說明書比沒有更糟（照著做卻找不到按鈕）。
- **更小的做法**：只做「寫進完成條件」，兩個檢查等真的漏過一次再加（AGENTS.md 的規則門檻也是犯過兩三次才加）。💡 先這樣，檢查的設計留到正文開工時定。
- 這也是正文不現在寫的理由之一：v1 還有一半功能在變動，現在寫等於在變動最大的時候開始付維護的代價。

## 6. 還沒談的（一輪一題）

1. **分段與開工時機**（第 5 節）：使用者 2026-11-22 同意先做骨架與樣式稿，正文等功能都合併才寫。試做完整版的那一節，使用者 2026-11-22 選「今天的複習」，已做出來（第 5 節〈試做的結果〉）。
2. **讀者**（第 2 節）：章節用「要做的事」分，不用「給家長」「給學生」分（對應 backlog 💬「說明書要不要也改掉『給家長』這個詞」）。範圍已定：只寫 Cards，三個軟體分開寫（D-219）。
3. **形式**（4-1）：Markdown 正本、自動產生網站、發布在 GitHub Pages、每節固定網址。三份說明書要不要放在同一個網站、用同一套樣式，也在這一題問。
4. **樣式稿**（4-2～4-4）：兩頁各兩三種版面，挑一種。情境頁使用者 2026-11-22 選「電腦用 B、手機用 A」（第 5 節〈試做的結果〉）；概念頁還沒做。
5. **章節表**（第 3 節）：一部一部確認，優先看有沒有可以刪的；附錄要多大。
6. **之後的新要求寫在哪**：寫進這張章節表，不再往 D-048 加補充（D-048 加一行指到這裡）。
7. **心智圖展開**（backlog 💬）：v1 用首頁的循環圖，完整版等 Mindboard。
8. **維護的做法**（第 5 節〈寫完之後怎麼跟著功能更新〉）：先只把說明書寫進功能任務的完成條件，兩個機械檢查等正文開工時再定。
