## 先讀這裡

- **要交付什麼**已經決定：v1 完工前交付完整的 HTML 使用說明書（[D-048](../../../../docs/decisions.md#d-048-使用說明書)、[D-130](../../../../docs/decisions.md#d-130-任務分成-v1-與第二階段)）。這份規畫談的是**內容怎麼排、長什麼樣子、什麼時候開始寫**。
- **定案一句話**（[D-221](../../../../docs/decisions.md#d-221-cards-使用說明書形式版面章節與維護)）：現在只做骨架（章節表、形式、固定網址）與樣式稿；正文等 v1 的功能任務都合併、畫面不再改才寫，例外是使用者要求先寫的節（〈自己寫卡組〉）。
- **只管 Cards**：Capture、Cards、Mindboard 的使用說明書分開寫，每個軟體一份（[D-219](../../../../docs/decisions.md#d-219-三個軟體的使用說明書分開寫)，使用者 2026-11-22 決定）；這份規畫只談 Cards 那一份。
- **要求的正本**：寫說明書時要寫什麼，原本散在 D-048 的 17 段補充與其他決定；第 3 節的章節表把它們收成一張表並標出來源。來源的全文仍以決定為準，這裡不重抄。

## 1. 為什麼現在規畫（和不做比，D-153）

不做＝照舊把要求累積在 D-048 的補充，v1 最後一次寫完。

1. **要求散在很多地方，有些已經被推翻**：D-048 有 17 段補充，其中三處後來改掉（「開始複習」改成一科一列、「只做某單元今天的卡」拿掉又恢復、深度三層改成不設頂）；另外約 12 條決定各指定一兩句（D-070、D-079、D-097、D-107、D-125、D-126、D-149、D-154、D-155、D-157、D-160、D-198），Cards 的 backlog 有 4 項、roadmap〈等觸發點〉有 2 列、plans 有 3 處。最後才整理，容易漏、也容易照著舊說法寫。收成一張章節表後，之後每個新要求直接寫進對應的章。
2. **外掛裡有幾個地方要連到說明書的某一節，現在沒有網址可以連**：設定頁連到「怎麼申請 API 金鑰」（D-048 2026-10-11 補充）、提醒一區與存檔受阻的提示連到「有檔案暫時讀不到」（D-154）。每一節的固定網址要先定，這些功能才收得了尾。
3. **形式會影響之後每一個任務怎麼留資料**：例如截圖要用示範用的 vault、不能拍到課本內容（D-003）與孩子的真實紀錄。先定下來，之後做功能時順手準備，不用最後重來。

代價：這一串的幾輪討論、一份規畫文件；之後多維護一張章節表（取代繼續往 D-048 加補充，沒有多一份）。

## 2. 讀者與寫法

**誰會讀、在哪裡讀**

| 讀者 | 要做的事 | 在哪裡讀 |
|---|---|---|
| 製卡與管理的人（多半是家長，也可能是自己用的學生或大人） | 安裝、製卡、審核、設定、備份、更新、排解 | 電腦，邊看邊做 |
| 每天複習的人（多半是孩子） | 怎麼複習、怎麼自評 | 手機，幾乎不讀；一頁、以圖為主 |
| 接手的人或 AI、想知道設計理由的人 | 附錄「規劃過程」 | 電腦 |

**寫法**（前五點已有決定或使用者的話，這裡只是集中）

章節照要做的事分，正文稱「你」，每節開頭一行小字寫適合誰看，不出現「給家長」「給學生」（D-221 第 5 點）。畫面上本來就寫「家長」的字照畫面寫（第 7 點）。

1. **從情境出發**：先寫「想做什麼 → 去哪裡按」，再說明背後的規則（D-048 2026-10-17 補充）。
2. **不期待有人從頭讀到尾**：使用者在 [D-169](../../../../docs/decisions.md#d-169-家長亂填出處是常態程式不猜看不懂就當場教) 說過「寫了也不會有多少家長讀」。畫面上當下說得清楚的，不靠說明書；說明書是拿來查的，外掛裡的連結直接到那一節。
3. **把讀者當成不熟悉電腦的人**（使用者 2026-11-07）：不要求 Git、命令列、改 JSON；一步一張圖。
4. **沒做完的不寫成可以用，沒走過一次的流程不寫**（AGENTS.md 底線、[D-198](../../../../docs/decisions.md#d-198-只做軟體不限制使用方式)）；學習效果寫成待驗證的目標。
5. **只寫軟體怎麼用**：不寫教家長怎麼教孩子的建議（使用者 2026-11-03）；「讓系統判斷得準」那三條是軟體的用法，照寫。
6. **會過期的內容標查核日期**：API 金鑰來源、iOS 的操作步驟、語音下載；每次發布新版前重查（D-048 2026-10-11 補充）。
7. **用詞照畫面上的字**：入口、目錄、當日卡、全部卡、提醒、學習目標、題目池、卡組；一個東西只有一個名字，附一頁名詞表。

## 3. 內容：章節表

**這張表怎麼維護**（D-221 第 6 點）：每一節只寫「這一節現在要寫什麼」的最新狀態。有新要求時直接改寫那一列、把它併進去，不往下加帶日期的補充，也不當成版本記錄；為什麼這樣定、什麼時候改的，留在決策紀錄與 git 的歷史。那一節的正文寫出來之後，正文就是最新版本，這裡只留連結與還沒寫進去的。之後新的說明書要求寫進這張表，不再往 D-048 加補充。

「現況」看 [progress-map](../../../../docs/progress-map.md)（2026-11-22：v1 的功能 35 項做完、13 項做了一部分、20 項還沒開工）。🟢 功能做完、畫面大致穩定；🟡 做了一部分或還會改；⚪ 功能還沒做，現在寫不了。

## 4. 樣式

### 4-1 形式：Markdown 當正本，自動產生網站

**定案**（D-221 第 2、3 點）：正本是 repo 裡的 Markdown、一節一個檔，合併進 `main` 後由 GitHub Actions 產生網站、發布到 GitHub Pages（和進度白板同一條路），每一節有固定的網址。Capture、Cards、Mindboard 三份放同一個網站、用同一套樣式、各佔一區，Cards 的網址帶 `/cards/`。還沒定的：用哪一個網站工具、網址怎麼命名（開工時定）；Portal 的說明放哪、另外兩份什麼時候寫。

- **用現成的文件網站工具**（例如 VitePress），不自己寫產生器：側欄、搜尋、手機版面都現成。用哪一個，開工時拿一頁實際試中文搜尋與手機版面再定。
- **每一節有固定的網址**（英文短名，例如 `/cards/troubleshoot/files-unreadable`），定了就不改；外掛裡的連結集中在一張表，網站之後搬到入口網站的網域時只改一處。
- **正本的資料夾**：Claude 寫第一節時先放在 `apps/Cards/docs/manual/`（資料夾對應網站的 `/cards/`，照 [architecture.md〈repo 結構〉](../../../../docs/architecture.md#9-repo-結構-d-208)外掛自己的文件放外掛的 `docs/`），使用者還沒表示意見。

### 4-2 一頁長什麼樣子

**版面**（D-221 第 4 點，看過第 5 節的樣式稿選的）：步驟頁電腦用「字在左、圖在右」，手機用「一步一張大圖」，依寬度自動切換（分界先用 600 像素）；概念頁理由收合。

情境頁固定四段：

1. **標題是想做的事**：例如「只想練某個單元」，不是「目錄畫面說明」。
2. **步驟**：編號，一步一句、一張圖；圖上只標這一步要按的地方。
3. **背後的規則**：預設收合，想知道的人再打開（例如單元數字的顏色怎麼算）。
4. **相關的節**：最多三個連結。

概念頁（第五部）：先一句話的結論，再一個真實例子（聲音單元、溶質與溶劑），最後才是設計理由。

### 4-3 視覺

- **延續複習畫面的安靜樣式**（[D-070](../../../../docs/decisions.md#d-070-複習畫面採用安靜樣式)）：白底、留白、系統黑體（D-180）；顏色只用在有意思的地方：記憶配色（D-062）和畫面上一樣，提示框只有三種（不能做的事、要注意、小提示）。
- **截圖**：電腦的統一寬度；iPhone 的放進手機外框、統一大小；深色與淺色只拍淺色。
- **示範用的 vault**：截圖一律在示範用的 vault 拍，卡組用自己寫的內容（例如聲音單元），不拍到出版社的課本（D-003）、孩子的姓名與真實紀錄。
- **圖**：首頁的循環圖與「整個複習流程」的流程圖畫成 SVG，手機上清楚；附錄的流程圖沿用 repo 現有的 mermaid。
- **首頁用循環圖當地圖**：每一站點進對應的章。這是「說明書用心智圖展開」（[experience.md](experience.md#其他待評估的操作與呈現)）的小做法；完整的心智圖版等 Mindboard 做出來再用它畫（D-221 第 7 點）。
- **每頁頁尾**：適用的外掛版本、最後查核日期。
- **外掛自己的畫面可以由程式拍**（2026-11-22 試做時驗證，見第 5 節〈試做的結果〉）：入口與複習畫面不用等 Cards 網頁版的建置，現在就能用腳本拍，還能自動標出要按哪裡。Obsidian 自己的畫面雲端拍不到，但在裝了 Obsidian 的電腦上也能用腳本拍（同一節）；仍要手動拍的只剩 iPhone 的系統畫面。

### 4-4 樣式怎麼挑

照之前挑複習畫面的做法：做兩頁真的內容當樣式稿，一頁情境頁（「今天的複習」，功能已在正式 vault 用了幾版）、一頁概念頁（「學習目標 ID 與題目指紋」），各出兩三種版面，使用者在電腦和手機上看過再選。

## 5. 什麼時候開始

**定案**（D-221 第 1 點）：A、B 現在做，C 一直做到正文開工，D 等觸發點。

| 段 | 什麼時候 | 做什麼 | 產出 |
|---|---|---|---|
| A 定骨架 | 現在（這一串） | 確認讀者、形式、章節表 | 這份規畫談定的部分 |
| B 外殼與樣式稿 | A 談定後，v1 的空檔，一件小任務 | 網站外殼、發布流程、每一節的固定網址、兩頁樣式稿 | 使用者挑定樣式；外掛裡的連結有地方連 |
| C 收要點 | v1 進行中，一直到正文開工 | 每個功能任務合併時，在章節表對應的章補「要寫的」一兩句；不寫正文 | 章節表保持最新 |
| D 寫正文 | 觸發點見下 | 先寫不靠截圖的（第五部、資料夾、不能做的事）→ 各情境章 → 安裝、更新、兩台裝置（最後）→ 附錄；截圖集中一次拍，iPhone 的和最後一次 iPhone 實機測試排在同一次 | 完整的說明書 |
| E 驗證 | 正文寫完 | AI 當沒看過 repo 的讀者，照說明書在測試用的 vault 從安裝走到第一次複習；再請一位沒用過的人照「快速開始」走一次 | v1 驗收的說明書那一項 |

**D 的觸發點**：v1 的功能任務都合併、最後一版裝到正式使用的 vault、之後沒有排定會改畫面的任務。

**為什麼正文不現在寫**

- v1 還有 20 項功能沒開工、13 項做了一部分，其中錯題補強、加深、考前抽測、提醒一區、調整製卡規則都是說明書的大章；入口與目錄的第三批還沒決定。現在寫的截圖和步驟，之後多半要重拍、重寫。
- 現在的使用者只有自己家，正文早寫出來沒有人讀；真正需要的時間點是給其他家庭之前，以及 v1 驗收。
- 安裝、更新、兩台裝置這三章受[入口網站與網頁版](<../../../Portal/docs/Claude Codex Discussion/2026-11-20-portal.md>)影響最大：孩子改在網頁複習的話，iPhone 那一半（保持下載、語音、換新版）會大改，所以排在最後。

**為什麼骨架和外殼不等到最後**：第 1 節的三點。B 是小任務（外殼、發布、兩頁），不靠還沒做的功能。

### 試做一節完整版

使用者 2026-11-22 要先挑一節以後比較不會變的，試做完整版（就是 B 的樣式稿做到完整），並問「安裝」適不適合。「安裝」是最會變的一節（給其他家庭的管道當時還沒定，後來是 [D-220](../../../../docs/decisions.md#d-220-給其他家庭的外掛上架-obsidian-官方目錄第一個外部家庭要裝時才上架)；iPhone 那一半受網頁版影響），所以改做「今天的複習」（情境頁）與「學習目標 ID 與題目指紋」（概念頁）。

### 試做的結果

使用者 2026-11-22 選「今天的複習」。試做稿在專案檔案 `使用說明書/今天的複習樣式稿/`（還沒進 repo），是整節寫完的情境頁：六個步驟、四個按鈕怎麼選、四個可能遇到的情況、七條背後的規則、三個相關的節。同一份內容做成三種版面。**使用者 2026-11-22 選：電腦用 B、手機用 A**（跟著螢幕寬度自動切換，分界先用 600 像素）：

| 版面 | 排法 | 手機上整頁的長度（約） |
|---|---|---|
| A 一步一圖 | 每一步文字在上、大圖在下，由上往下讀 | 6,800 像素 |
| B 圖文並排 | 字在左、圖在右；手機上圖縮成小圖，點一下放大 | 4,200 像素 |
| C 左右滑 | 步驟排成一排卡片，左右滑著看；後面的步驟要滑才看得到 | 3,900 像素 |

試做時發現的：

1. **截圖可以用程式拍**。外掛的入口與複習畫面（`src/ui` 的 `openEntry`、`openReview` 加 `src/state`）不靠 Obsidian 就能在瀏覽器裡跑：把 `obsidian` 模組換成替身、檔案放在記憶體，用 Playwright 照劇本操作並截圖。21 張大約 1 分鐘，還能記下每一步要按的按鈕在哪裡，自動畫出標示。試作在專案檔案 `使用說明書/截圖工具/`。
2. **雲端拍不到的**：Obsidian 自己的畫面（編輯畫面、工具列、設定頁、命令面板）和 iPhone 的系統畫面。Obsidian 的畫面改在裝了 Obsidian 的電腦上用腳本拍（見下面〈自己寫卡組〉那一段，編輯畫面已做成；設定頁與命令面板同一個做法，還沒試）；iPhone 的系統畫面仍要手動拍。
3. **和實機不完全一樣的**：Markdown 的渲染是簡化的替身，字型是 Noto Sans TC（iPhone 上是蘋方）。正式採用前要拿幾張和 iPhone 實機的畫面對一次。
4. **示範用的卡組要夠多**：試作只有 9 張，入口每一科都顯示「1 分鐘」；正式的示範 vault 每科要有二三十張，時間與進度才像真的。
5. **每一條規則都要對過程式或決定才寫**：這一節對了 D-062、D-069、D-070、D-084、D-095、D-096、D-120、D-160 與 `Review.tsx`。
6. **這一稿先做的假設**：對複習的人說「你」（後來定案，D-221 第 5 點）；「相關的節」指向的三頁還沒寫。

**概念頁「學習目標 ID 與題目指紋」**（4-4 的另一頁，2026-11-22 做出來，屬於使用者同意的「先做骨架與樣式稿」）：試做稿在專案檔案 `使用說明書/ID與指紋樣式稿/`，照 4-2 的「結論 → 例子 → 理由」寫完：結論、一段標出 ID 與指紋的筆記、改錯字前後的對照、兩者的比較、七種改法各自會怎樣、五條設計理由、三條保護、不能做的事。同一份內容三種版面。**使用者 2026-11-22 選：B 理由收合**：

| 版面 | 排法 | 手機上整頁的長度（約） |
|---|---|---|
| A 全部展開 | 所有內容攤開；電腦上右邊有本頁目錄 | 5,500 像素 |
| B 理由收合 | 結論、例子、「會怎樣」的表先看，理由與保護收成一題一題，和步驟頁「背後的規則」同一種做法 | 4,400 像素 |
| C 圖解卡片 | 筆記的例子放大當開場，比較改成兩張卡，電腦上後面排成兩欄 | 5,800 像素 |

做這一頁時發現的：

1. **D-048 的補充有兩句已經被後來的決定改掉**：「刪掉或改掉 ID，進度會歸零而且沒有提示」（D-134 起，電腦的編輯器鎖住 ID，在 Obsidian 以外弄丟時先停出、由家長選）、「複製卡片時程式會自動換新的 ID」（D-157 起改成先停、家長選）。寫正文時每一句都要查最新的決定，不能直接抄 D-048 的補充；這也是 D-221 第 6 點（新要求寫進章節表）的理由之一。
2. **例子用真的值**：這一頁的指紋是照外掛的算法算的（和截圖工具跑出來的紀錄對過），複習紀錄那一行也是工具實際寫出來的。之後可以由同一支腳本產生，不用手抄。

**正式寫的第一節〈自己寫卡組〉**（使用者 2026-11-22：製卡方式裡，自己寫這一部分不太會再改，先正式寫進說明書）：正本在 [`apps/Cards/docs/manual/make/write-your-own-deck.md`](../manual/make/write-your-own-deck.md)，寫法與截圖的標記見[那個資料夾的說明](../manual/README.md)；可以看的頁面在專案檔案 `使用說明書/自己寫卡組/`。只寫穩定的核心，還會變的列在那一節最後。五種製卡方式的現況：自己寫（做好了）、AI 製卡的複製貼上（做好了）、加深、錯題補強、補記憶錨點（後三種還沒做完）。

做這一節時 Claude 先定的（使用者還沒表示意見）：正本的位置（4-1）。圖檔放進 repo（使用者 2026-11-22 問為什麼不放之後改的），在那一節旁邊的 `img/`：Obsidian 自己的畫面只能在裝了 Obsidian 的電腦上拍（雲端下載不到 Obsidian），建置時產生不了，圖要有固定的地方放；放進 repo 之後 GitHub 上直接看得到圖，建置也不用再跑一次截圖。代價是 repo 變大：現在六張共 0.4 MB，整本 60～80 張估計 10 MB 以內，畫面改了才重拍。

**Obsidian 的編輯畫面也能用程式拍**（2026-11-22 在使用者的電腦上做成，六張）：用獨立的設定資料夾另外開一個 Obsidian、只開新建的示範 vault，Playwright 接上去照劇本操作與截圖，不碰真的設定與真的 vault。雲端下載不到 Obsidian，所以只能在裝了 Obsidian 的電腦上跑。腳本與注意事項在專案檔案 `使用說明書/截圖工具/obsidian/`。兩件事記下來：

- **拍的時候順便對出文字的錯**：第一版有三處和畫面不一樣（存檔與啟用按鈕上沒有字、只有圖示；程式補的編號在畫面上是寫著「ID」的小標籤；存檔的通知只列紅色的、不列橘色的），已照畫面改。之後每一節的截圖腳本都要回報畫面和文字不一樣的地方。
- **電腦畫面的截圖很寬、空白多**：正本放整張；頁面上放裁過的重點（按鈕那一角、清單那幾行），點了看整張。裁切的範圍現在寫在專案檔案的 `crop.py`，建置做出來時搬進建置設定。存檔通知原本貼在視窗最上緣，截圖時往下移到標題列下面，只改位置。

💡 還沒同意的：把截圖工具搬進 repo、改成相對路徑，當成說明書建置的一部分。

### 寫完之後怎麼跟著功能更新

使用者 2026-11-22 問：說明書會不會跟著功能自動更新、維護代價大不大。不會完全自動；目標是使用者幾乎不用管。

| 哪一塊 | 誰做 | 做法 | 代價 |
|---|---|---|---|
| 發布 | 自動 | 正本合併進 `main`，網站自己重新產生 | 無 |
| 文字 | 做功能的 AI | 「改到的說明書那幾節」寫進功能任務的完成條件，同一個 PR 一起改 | 每個任務一到三節、每節幾段 |
| 不漏改 | 機械檢查（之後再做） | ① 一張「程式的哪一區對應說明書哪幾節」的表，PR 改了那一區卻沒動說明書就提醒（可以寫一句「說明書不用改」放行）；② 說明書裡寫到的按鈕與畫面名稱，在程式的字串裡要找得到。兩個都接在現有的文件檢查 | 兩個小工具與它們的測試；表要跟著章節維護 |
| 截圖 | 使用者（iPhone）、AI（電腦） | 會常改的畫面少放圖；發布前由工具列出這一版要重拍的圖，和上線前的 iPhone 實機測試排同一次；外掛自己的畫面（入口、複習）可以由腳本重拍（〈試做的結果〉第 1 點），Obsidian 的畫面在裝了 Obsidian 的電腦上由腳本重拍，手動的只剩 iPhone 系統的畫面 | 原本是維護的主要代價；腳本能拍的部分降到跑一次腳本 |
| 會自己過期的 | AI，每次發布前 | API 金鑰來源、iOS 步驟、語音下載照查核日期重查；要實機的併進 iPhone 測試 | 每版一次 |

- **定案**（D-221 第 8 點）：先只做「寫進驗收」（寫在[工作流程規範〈任務說明〉](../../../../docs/agents/workflow.md#任務說明)）；兩個機械檢查等正文開工、或真的漏改過一次再做。截圖腳本本身會對出畫面和文字不一樣的地方，先擋掉一部分。
- 這也是正文不現在寫的理由之一：v1 還有一半功能在變動，現在寫等於在變動最大的時候開始付維護的代價。
