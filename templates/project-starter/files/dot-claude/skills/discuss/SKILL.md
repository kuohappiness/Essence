# 討論

一件事從點子到完成的路線、每類文件的用途與連結寫法，見 `docs/workflow.md`；這裡只寫怎麼討論。

1. **一輪只問一題**：先把要決定的事列成決策樹，挑不依賴其他未決題目的最上游那一題問，等使用者回答再問下一題。不要一輪列出多題。
2. **先查再問**：提問前查相關的舊決定（`docs/decisions/README.md` 的索引，只讀相關的幾條）；新提案和舊決定衝突時，明講是哪一條、為什麼值得重談。repo 裡查得到的事實自己查，不問使用者。
3. **提案不是決定**：每題附上你的建議答案，標 💡。
4. **先問會不會明顯更好，再比不做**：每個提案寫出 ① 優勢、不做會怎樣：具體壞在哪、多常發生、影響誰；② 做的代價：新增的程式、文件、測試，以後要維護的，使用者要多學的；每一項寫出解決得了嗎、怎麼解決；③ 更小的做法：只改現有的、延後，或先做個小實驗試一次，和完整做法差距不明顯就選它。優勢明顯、代價解決得了就建議做，工作量不算理由；好處很小又費力，或代價解決不了，才建議不做。
5. **優先刪減**：每題談完，檢查有沒有東西沒有讓結果明顯變好，可以刪掉或延後。
6. **用真實的例子驗證**抽象設計；試一次就知道的問題，建議先做個小實驗，不在對話裡猜。
7. **問清楚範圍**：使用者說「現在不用考慮某件事」時，先問是暫時不做還是以後都不做、影響哪個範圍，再動已經寫好的檢查或測試。
8. **有獨立查核者時**，重大決策的第一輪各自獨立，做法在模板來源的成長包。

## 結束

- 談定的題目：用 Skill tool 載入 "decision"，先判斷要不要寫成決定（小事在那件事現在的位置寫「使用者 YYYY-MM-DD 同意」）。
- 沒談完：還沒解的問題與目前的傾向寫進 `docs/backlog.md`〈待處理〉的那一項，同一個問題只有一份主文。
