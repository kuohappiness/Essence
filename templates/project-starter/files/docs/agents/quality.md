# 程式品質：本專案的設定

給 `code-quality` skill 讀。這裡只寫對應與連結，通用的做法在 skill 裡。

## 角色

| 角色 | 由誰擔任 |
|---|---|
| 規劃者 | 【待填：誰寫任務規格、做大的設計，用什麼推理等級】 |
| 實作者 | 【待填：誰寫程式】 |
| 獨立查核者 | 【待填：誰做合併前的獨立審查；沒有第二個 AI 時，由沒參與實作的新 session 擔任】 |
| 整合者 | 【待填：誰對照規格、核對審查的發現、合併】 |

同一個 agent 檢查自己的成果不算獨立審查，所以驗收條件要先寫成能用程式判斷的句子。困難的除錯照〈卡關時的升級〉。

## 本機或雲端

任務開始時判斷，整件在同一邊做：

- **使用者的電腦**（電腦要開著）：【待填：哪些工作一定要在使用者的電腦做，例如要用本機的帳號、裝置或私人檔案的】
- **雲端**（電腦可以關）：其餘的。在使用者的電腦上遇到這類工作，開工前提醒使用者可以改到雲端做。
- 雲端做到一半發現要使用者的電腦：推分支，在入口寫下進度與下一步，提醒使用者接手。
- 雲端 session 只推自己的分支，不直接推 `main`；做完開 PR。
- 雲端 session 的環境由 `.claude/hooks/cloud-setup.mjs` 準備（設 git hook、把 repo 的 hook 接到這台機器）。雲端讀不到使用者電腦上的記憶，會影響做法的規則要寫進 repo。

## 檢查指令

- `node tools/check.mjs`：提交前與 CI 都跑。查金鑰、還沒填的空格、連到不存在的檔、git hook 的執行權限。不用安裝套件，Node 20 以上直接跑。
- 提交前：`.githooks/pre-commit` 跑 `node tools/check.mjs --staged`，只看暫存區。
- CI（`.github/workflows/check.yml`）：只在 push 跑；最後一關叫 `gate`，`main` 的保護規則要它綠燈才合得進去。

## 測試分兩類

問「做錯了，之後改版改得回來嗎？」，一項一項分，同一件工作可以兩類並存：

- **先看正常流程**：會擋住或弄錯正常使用的，照原本的驗收做完，不延後。之後才看少見的情況。
- **第 1 類**：上面的高風險範圍涵蓋的，以及會默默弄壞資料的；合併前做足。說不準的歸這一類。
- **第 2 類**：其餘少數例外狀況的測試、為很少見的情況多做的功能；可以延後，寫成 [backlog〈技術債〉](../backlog.md#技術債)開頭「補測：」或「補做：」的一列。延後功能時，開放的入口要能走完一條安全的路徑，否則合併前先關住入口或做完那條路徑。

## 卡關時的升級

除錯照 code-quality 的 `debug.md`，列出的假設都被推翻、或做不出能重現的指令，就算卡關。依序：

1. 同一個模型換成較高的推理等級，從除錯做法的第 1 步再做一次。
2. 交給獨立查核者從頭查：只給重現指令、錯誤訊息、相關檔案與基準 commit，不給前面的假設與推論。
3. 都解不了，換能力更強的模型，附交接說明：目標、試過的做法、各自為什麼不對、目前的證據。

每升一級先跟使用者說一聲；會用掉大量額度的，先問使用者。
