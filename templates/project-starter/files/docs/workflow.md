# 工作流程：一件事從點子到完成

這是這條路線唯一的現行版本。規則寫在 `AGENTS.md`，決定只記為什麼，怎麼做寫在這裡。

## 路線

```text
點子
 │ 記下來
 ▼
docs/backlog.md〈待處理〉………… 短點子、待決問題、技術債、已知的限制
 │ 要做決定：這一項搬到〈已轉出〉，項目下加一行「→ <下一站>（日期）」
 ▼
討論 ………………………………………… 一次問一題、附建議、和「不做」比較（discuss）
 │ 使用者明確同意
 ▼
docs/decisions/D-xxx.md ……… 一條決定一個檔，寫「來自」；索引加一行（decision）
 │ 動手做
 ▼
分支 → PR → 檢查綠燈 → 合併
 │
 ▼
docs/roadmap.md〈已完成〉…… 加一列：日期、做了什麼、連到決定或 PR
```

- 可以跳站：小事談定後直接做，不必寫成決定（〈什麼才寫成決定〉）。
- 做完的文件不刪不搬，只改狀態；舊連結才不會壞。

## 每類文件

| 文件 | 用途 | 什麼時候進來 | 終點 |
|---|---|---|---|
| `docs/roadmap.md` | 狀態板：〈現在在哪裡〉正在做的事、〈等觸發點〉條件到了才做的事、〈已完成〉 | 開工時在〈現在在哪裡〉加一列 | 做完把那一列移到〈已完成〉，日期寫合併那天 |
| `docs/backlog.md` | 〈待處理〉放點子、待決問題、技術債、已知的限制；〈已轉出〉放已經往下走的項目 | 有新點子、發現問題、測試延後時 | 往下走時搬到〈已轉出〉，加「→」；技術債補完刪掉那一列 |
| `docs/decisions/` | 一條決定一個檔，`README.md` 是索引與寫法 | 使用者明確同意，又是〈什麼才寫成決定〉那幾類 | 不刪；被新的決定修改或取代時，在新的那條寫明 |
| `docs/agents/quality.md` | 程式品質的專案設定：角色、檢查指令、高風險範圍、測試分兩類 | 第一個 session 填好 | 專案的做法改了就跟著改 |

## 連結

- **來自**：新的一站在開頭寫一段 `來自：<連結>`，說它是從哪裡來的；從好幾處來的用「、」接。沒有上一站寫「使用者提出」。
- **→ 下一站**：上一站加一行 `→ <連結>（YYYY-MM-DD）`，「→」後面直接接連結；backlog 寫在那一項的下一行。拆成好幾站就寫好幾行。寫了不再改。
- 連到別的文件用相對連結；連到某一節時帶標題的錨點。

## 什麼才寫成決定

- **寫成決定**：做錯了改不回來的（資料格式、對外的介面、會刪改使用者資料的行為）、整個專案都要照著做的規則、產品範圍（做什麼、不做什麼）。拿不準就寫成決定。
- **不寫成決定**：其他小事。使用者同意後，在那件事現在的位置（backlog 的那一項、PR 的說明）寫「使用者 YYYY-MM-DD 同意」加一句內容。
- 寫法見 [decisions/README.md](decisions/README.md)。

## 開工前先看

照舊版的標準或工具做完，新版一定案就要重做。開工改檔（程式、規則、標準、工具、規範文件）與取決定編號之前：

- **開著的 PR**：`node tools/in-flight.mjs [要改的路徑…]` 列出每個開著的 PR 改到哪些檔、新增了哪些決定；最後一行是下一個可以用的決定編號。有 PR 沒查完時它不給編號，照它的說明補齊再跑。
- **還沒開 PR、正在談的事**：看正在跑的討論串的標題，和手上的工作有關的才讀。
- **「同一樣東西」不只同一個檔**：手上的工作照著用的標準、規則或工具正在被改，也算。
- **有重疊時**：把工作拆開，不受影響的照做；會受影響的那段等那邊合併或談定再做，請那邊做完時通知；告訴使用者哪一段在等、等的是哪一串的什麼。只是動到同一個檔、改的地方不相干的，照做，合併時處理衝突。
- 分支上寫了決定，合併前再跑一次，確認編號沒有被搶先用掉。

## 進度放檔案還是 Issues

預設放 repo 的檔案（`docs/roadmap.md`、`docs/backlog.md`）：AI 每個 session 開工直接讀得到，不必另外連 GitHub。有下面的情況再考慮改用 GitHub Issues：

| 情況 | 放檔案 | 改用 Issues |
|---|---|---|
| 誰在更新進度 | 只有 AI 與一兩個人 | 有不寫程式的人要追進度、留言 |
| 純狀態更新造成的衝突 | 很少 | 常常為了改一行狀態解衝突、等 push |
| 接手的 session 找不找得到下一步 | 找得到 | 常常找不到最新的下一步 |
| 一件工作的大小 | 不一定 | 多數都能由一個 PR 結案 |

改用 Issues 前，先拿 3～5 件新工作試行，再決定要不要全部改。

## 成長條件

專案長大到下面的條件，才去模板來源的 `growth/` 拿對應的做法；條件還沒到的不先加。

| 條件到了 | 加什麼 | 去 `growth/` 拿 |
|---|---|---|
| 第一次要把工作交給另一個 session，或規格寫超過一段 | `docs/tasks/`、入口的狀態行；狀態板改由工具整份產生 | 任務說明的做法，加 `tools/status-board.mjs` |
| 一個主題要談好幾輪 | `docs/plans/` | 規劃文件的做法 |
| 有第二個 AI 可以查核，高風險範圍也不是空的 | 討論稿、第一輪各自獨立、合併前的獨立審查、skill 的第二份副本與一致性檢查 | 第二個 AI 的做法 |
| 有一份文件超過約 2 萬字，或決定超過 30 條 | 只讀一節的小工具；決定的索引改由工具產生 | `tools/section.mjs`、`tools/decisions-index.mjs` |
| repo 公開，又有不能公開的名字或路徑 | 私人字詞檢查，清單只放使用者的電腦 | 私人字詞的做法 |
| 專案開始裝套件（有鎖檔） | 雲端開場加裝套件；提交前比對已裝的套件和鎖檔 | 套件的做法 |
| 第一個里程碑完成 | 回顧與安全檢查 | `code-quality` 已經內含，照它的 `milestone.md` 做 |
| 出現第二個子專案 | 每個子專案自己的資料夾與規則 | 子專案的做法 |

模板來源：https://github.com/kuohappiness/Essence 的 templates/project-starter（commit 收尾時填，日期收尾時填）
