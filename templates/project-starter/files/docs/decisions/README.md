# 決定

一條決定一個檔，檔名是編號（`D-001.md`）。決定只記為什麼；怎麼做寫進規範文件（`AGENTS.md`、`docs/workflow.md`、`docs/agents/quality.md`），由規範文件連回這裡。什麼才寫成決定見 [workflow.md〈什麼才寫成決定〉](../workflow.md#什麼才寫成決定)。

## 索引

新決定加在最下面一行；狀態改了（被修改、被取代）同時改這裡。

| 編號 | 一句話 | 日期 | 狀態 |
|---|---|---|---|
| [D-001](D-001.md) | 這個專案採用這套初始架構 | 【待填：日期，YYYY-MM-DD】 | ✅ |

## 一條決定的寫法

- **編號**：跑 `node tools/in-flight.mjs`，用最後一行的「下一個可以用的編號」（`main` 與開著的 PR 都算過）。編號不重用。分支上寫的決定，合併前再跑一次；兩個分支用到同一個編號時，合併會直接報檔案衝突，晚合併的那個改號。
- **檔名**：`docs/decisions/D-xxx.md`，三位數字。
- **內容**照下面的樣子；「曾考慮的做法」必寫，第一項是「不做」：

```markdown
# D-xxx 名稱

✅ YYYY-MM-DD｜來自 <上一站的連結，沒有就寫「使用者提出」>｜修改 [D-yyy](D-yyy.md)（第 n 點）｜取代 [D-zzz](D-zzz.md)

一句話：<一句話說決定了什麼>

## 決定

1. ……

## 理由

- ……

## 曾考慮的做法

- 不做：不做會怎樣、為什麼不夠。
- ……
```

- 狀態行用「｜」分段；沒有修改、取代就不寫那一段。被修改或取代的舊決定，只改索引的狀態欄（寫「已修改，見 D-yyy」或「已取代，見 D-zzz」），舊檔不改。
- 寫完：索引加一行；「來自」連到的上一站加一行 `→ [D-xxx](…)（YYYY-MM-DD）`；把規則寫進受影響的規範文件。
