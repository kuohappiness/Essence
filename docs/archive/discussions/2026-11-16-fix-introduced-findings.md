# 修 L2 的發現時帶出新問題

2026-11-16｜討論摘要，非逐字紀錄。專案討論串「評估以 19 個好習慣整合開發流程」，使用者與 Claude 談，Fable（xhigh）看了兩輪；結論寫成 [D-207](../../decisions.md#d-207-l2-的發現先分一定修可記限制交使用者選修法先收窄最後才加機制)。這一題使用者決定不送 Codex。

## 討論經過

1. **使用者提出**：Codex 審核的結果常出現 edge case，Claude 為了修這個 edge case 又產生新的問題。
2. **Claude 數 2026-11-09～11-15 的七件 L2**：第一輪 44 項；後面幾輪 55 項，37 項是修了沒修乾淨，16 項標「修正引入」，和修正無關的只有兩三項。修正引入的多半是修法多加了一道機制（重試、逾時、再讀、再檢查、計數、清字元），例如紀錄缺口的 R5、R11、R17。現有的 [D-200](../../decisions.md#d-200-l2-的發現鏈待驗問題連兩輪沒驗先讀宿主程式整類修過仍失守就換前提)、[D-202](../../decisions.md#d-202-l2-的發現先估發生機率極低的記成已知的限制) 管不到這一類。提案：修法多加機制時，交回前先自己攻擊它，各寫測試；能讓情況不發生就不加機制。
3. **使用者要 Fable 的看法**。Fable 第一輪：
   - 數字：後面幾輪它數到 66 項，修正引入 17～18、延續 46；第一輪每修一項，後面平均再多出約 1.5 項。
   - 根因：修法習慣再加一道機關（英文排序 R6：Codex 建議限純文字，Claude 選了刪符號）；不值得修的也修了（紀錄缺口 R4 約 1.4×10⁻⁵ 仍修；D-202 之後英文排序六項全修、沒寫機率；對聯卡以「修起來不大」為由修）；擔心的地方寫給 Codex、自己沒先跑（對聯卡的 R5、R7）。測試只對著重現不是主因。
   - 對 Claude 的提案部分同意：「能讓情況不發生就不加機制」放最前面；「加了機制就各寫測試」不建議（D-197 試過類似的沒省輪數，機制清單也漏了加欄位、放大範圍、加狀態）。
   - 建議：修之前多寫「發生條件與機率」「修法類型」兩欄，類型依序是不修、收窄、改用已有的唯一來源、加機制；「特別請看」附測試名；去格式整併成一處（另開任務）。
4. **使用者決定**這一題在討論串談定，不送 Codex；並追問提案有沒有考慮到應該避免代價太大的決定。
5. **Claude 回應**：只考慮到一半，順序照修法的形狀排，沒拿修法的代價比問題的害處。補了「修法的代價」一欄、「代價大於好處就不修」、只有會弄壞紀錄或改不回來的一定修、改到看得到的行為或大改結構的先問使用者。
6. **使用者要 Fable 再看一次**。Fable 第二輪：
   - 「一定修」要收緊成「正常使用就會碰到的；會默默弄壞資料或改不回來、機率又不是極低的」，否則紀錄缺口 R4 那種照字面又得修。
   - 「代價大於好處」太主觀，改成不用比：實作者自己能決定不修的只有「機率極低」與「走不到並附證據」；其餘的，不加機制、不必再送 L2 的就修，否則連同「不修」集中一次交使用者選。
   - 第 3 代不再加機制，回到收窄或唯一來源，併掉 D-200 的換前提那條；review.md 是通用 skill，不寫專案的 D-ID。
   - 不確定：問使用者的次數會不會太多、「極低」的界線，都沒量過。
7. **使用者選 Fable 修過的最終條文**（2026-11-16），寫成 D-207。
