# 工作流程：一件事從點子到完成

這是這條路線唯一的現行版本（[D-214](../decisions.md#d-214-工作流程一件事一個現在位置反方向由工具算) 第 1 點）。檔案放在哪個資料夾見 [architecture.md §9](../architecture.md#9-repo-結構-d-208)；決定只記為什麼，怎麼做寫在這裡。依據：D-214、[D-215](../decisions.md#d-215-狀態留在-repo獨立的第一輪決定的門檻只讀需要的那一段)、[D-217](../decisions.md#d-217-狀態只寫在入口狀態板與已完成由工具產生)。

## 路線

「外掛」指 `plugins/<外掛>/`；只和一個外掛有關的放它的 `docs/`，其餘放最上層的 `docs/`（[D-213](../decisions.md#d-213-任務與討論稿放進-docs外掛專用的放外掛的-docs)）。

```text
點子
 │ 記下來
 ▼
backlog〈待處理〉………………… 短點子、待決問題、技術債
 │ 需要展開：這一項搬到〈已轉出〉，項目下加一行「→ plans/A（日期）」
 ▼
plans/A.md ……………………………… 還在規劃的細節；開頭寫「來自」
 │ 要做決定
 ▼
討論 …………………………………………… 一次問一題、附建議、和「不做」比較（essence-discuss）
 │ 重大的：Claude Codex Discussion/ 的討論稿，第一輪各自獨立，一致才交給使用者
 │ 使用者明確同意
 ▼
decisions.md（D-ID）…………… 寫「來自」「修改 D-xxx」與主題、一句話（essence-decision）；上一站加「→ D-xxx」
 │ 同步規範文件；索引、往前的鏈、「現行寫在哪」由工具算
 │ 可以交付實作
 ▼
tasks/<任務>.md ……………………… 規格與驗收；開頭寫「來自」；roadmap 的狀態板手寫一列（工作、入口）
 │ 實作 → L1 → 高風險的 L2 → 合併
 ▼
入口的狀態行改「已合併｜完成：一句話」→ node tools/roadmap-sync.ts 把那一列移到〈已完成〉；progress-map 改符號
```

- **一件事同一時間只有一個現在的位置**：沿著「→」走到的最下游那一站（D-214 第 2 點）。
- 可以跳站（短點子直接談成決定）、拆分（寫好幾行「→」）、合併（「來自」連好幾處）、退回（下游寫「來自」連回上游，工具遇到走過的站就停）。
- 每一站只寫兩種連結：自己的「來自」、上一站的「→ 下一站」，都只寫一次（〈連結〉）。往前的「後續見」由工具反推。
- 做完的任務、討論稿與 plans 不刪不搬，只改狀態行（[D-143](../decisions.md#d-143-歸檔原則每類文件都有終點不設字數上限)）。

## 每類文件

### backlog

- **用途**：任務與第二階段候選的統一入口（[D-130](../decisions.md#d-130-任務分成-v1-與第二階段)）、待決問題、技術債與已知的限制。新點子保留原意與來源。
- **分區**：二級標題只有 `## 待處理`、`## 已轉出`，依這個順序（文件檢查擋）；其他的分類放在這兩節底下。AI 只讀〈待處理〉。
- **轉出**：一項需要展開、談成決定或做成任務時，搬到〈已轉出〉（不刪：舊連結不壞，原意與來源留著），在項目下一行加 `→ <下一站的連結>（YYYY-MM-DD）`。〈待處理〉裡不能有「→」。
- **技術債**：最上層 backlog〈待處理〉〈技術債〉的表（[quality.md〈技術債清單〉](quality.md#技術債清單)）；補完的那一列刪掉。

### plans

- **用途**：還在規劃的細節，一個主題一份，不按日期重開（[plans/README](../plans/README.md)）。
- **進來**：backlog 的一項需要展開；開頭寫「來自」。
- **狀態行**：新格式（〈入口的狀態行〉）；常用規劃中、討論中、等觸發點。定案的部分換成一句加 D-ID。整個主題都轉成決定或任務，寫 `已結案 → <下一站>`。
- **當入口**：一件工作要好幾份任務（分批做），狀態板的入口是它的 plans（D-217 第 1 點）。

### 討論稿

- **用途**：重大決策點 Claude 與 Codex 輪流回覆，一致才交給使用者（[D-106](../decisions.md#d-106-claude-與-codex-的協作流程)）；同一議題接續同一份 `YYYY-MM-DD-主題.md`，只在處理那個議題時讀。
- **第一輪各自獨立**（D-215 第 4 點）：選項還開著的題目，依序是〈提問稿〉、〈第一輪：Claude〉〈第一輪：Codex〉、〈第二輪：交叉〉、〈請使用者決定〉；細節在 [essence-discuss](../../.claude/skills/essence-discuss/SKILL.md)。
- **狀態行**：討論中；談定寫 `已結案 → [D-xxx](…)`，擱置寫 `暫停（原因）`。
- 沒有討論稿的重要討論，結束時在 `docs/archive/discussions/` 寫摘要，不當規格。

### 決定

- **什麼才寫成 D-ID**（D-215 第 5 點）：改不回來的（資料格式、學習目標 ID、複習紀錄、排程、相容）、跨外掛或整個專案的規則、產品範圍。其他小事，使用者同意後記在那件事現在的位置，寫「使用者 YYYY-MM-DD 同意」。拿不準就寫 D-ID。
- **新寫法從 D-218 起**（D-214 第 10 點）：

  ```markdown
  ## D-xxx 名稱

  ✅ YYYY-MM-DD｜來自 [plans/A](plans/A.md#一節)｜修改 [D-yyy](#…)（第 n 點）、補充 [D-zzz](#…)｜取代 [D-www](#…)

  主題：<索引的主題之一>｜一句話：<一句>

  適用：全部
  ```

  - 狀態行用「｜」分段：「來自」「修改」「補充」「取代」開頭的段裡的 D-ID 是上游，要存在而且編號比自己小。
  - 主題只能是索引既有的 8 個之一；一句話不能空。
  - 不改舊決定的狀態行：舊決定的「後續見」「已取代」由工具從新決定反推。
- **寫完**：跑 `node tools/decisions-index.ts` 重產索引（索引沒重產，commit 擋）；上一站加 `→ [D-xxx](…)（日期）`；把規則同步進規範文件。決定不列進 roadmap 的〈已完成〉：白板的「最近定案」從決策紀錄產生。
- **查**：`node tools/decisions-index.ts D-xxx` 印這條全文、「現行寫在」（從規範文件反推的出處）、直接修改它的決定的〈決定〉、更深的一句話；`--deep` 全印。現行規則以「現行寫在」列的規範文件為準。

### 任務說明

- **用途**：交給實作或查核的規格、驗收與測試；審查請求與報告也放這裡。先和「不做」比較（[D-153](../decisions.md#d-153-每個新決定與新任務先和不做比較)）；寫法照 code-quality。
- **進來**：可以交付實作；開頭寫「來自」。開工時在 roadmap 的狀態板手寫一列（〈roadmap〉）。
- **狀態行**：新格式；收尾寫 `狀態：已合併｜完成：<一句話>｜等誰：—`。延後的測試寫在〈結果〉（[D-195](../decisions.md#d-195-測試分兩類改不回來的做足其餘延後但不漏)、[quality.md〈測試分兩類〉](quality.md#測試分兩類)）。
- 發版任務收尾時，「完成」以「正式 vault 升到 `x.y.z`」開頭：白板從這句認出現在的版本。

### roadmap

最上層 `docs/roadmap.md` 是入口，放跨外掛的工作；每個外掛的 `docs/roadmap.md` 放自己的。每份都有這三節，依這個順序（文件檢查擋）：

1. **〈現在在哪裡〉**：狀態板，欄是 `工作｜狀態｜下一步｜等誰｜入口`。手寫的只有「工作」與「入口」，只在開工時加一列；入口一格剛好一個連結，連到有新格式狀態行的文件（任務說明、討論稿、plans、card-rules）。其餘三欄由工具從入口讀出來。一份入口只在一份 roadmap 有一列。AI 開工讀這一節就好。
2. **〈等觸發點〉**：表 `工作｜觸發點｜入口`。入口狀態是等觸發點的列，工具從狀態板搬過來、觸發點取「下一步」；改回進行中，工具搬回狀態板。入口只有 D-ID、或連到沒有狀態行的紀錄（例如 `card-rules/trials.md`）的列手寫，工具不動。
3. **〈已完成〉**：表 `日期｜工作`，整個由工具產生：入口的狀態變成已合併或已結案，工具把那一列移到最上面，寫成 `**<工作>**：<完成>（<狀態值>，[入口](…)）`，日期取收尾的 commit。commit 時和 HEAD 比：新加的列要是工具寫的、日期是收尾那天、一份入口一筆；舊的列只能改連結的目標；狀態板的列不手動刪（入口結束了卻沒有新的完成列，擋下）。不設列數上限、不搬去封存；2026-11-21 以前的在 [已完成（封存）](../archive/roadmap-completed.md)。

**改了入口的狀態**：跑 `node tools/roadmap-sync.ts`，再 `git add` 改到的 roadmap。commit 時 `roadmap-sync --check --staged` 比對，對不上就擋下並印這兩步（D-217 第 5 點）。roadmap 只為了改狀態而手改，會被改回來。工作流程上線前開的分支，手寫的〈已完成〉列合併時會被擋：刪掉那一列，入口的狀態行改成 `狀態：已合併｜完成：…｜等誰：—`、狀態板加回那一列，再跑同步。

**進度白板**（`tools/roadmap-board.ts` → GitHub Pages）：狀態板合併各份〈現在在哪裡〉；「最近完成」合併各份〈已完成〉；「最近定案」是決策紀錄最新的 5 條 ✅，新寫法的再加「現在在哪」；正式 vault 的版本與待發布只看 Cards 的 roadmap。〈等觸發點〉不上白板。

### progress-map

功能地圖（`docs/progress-map.md`）；一項功能合併或可用時改符號。

## 入口的狀態行

標題下第一個非空行，一般段落（不在引用框、程式碼區塊裡）：

```text
狀態：<狀態值>｜下一步：<一句>｜等誰：<值>
狀態：已合併｜完成：<一句>｜等誰：—
```

- 剛好三欄，用全形「｜」分；欄裡不能再有「｜」。
- **狀態值**：規劃中、討論中、實作中、待審、待實機、等觸發點、已合併、已結案、`已結案 → <D-ID 或連結>`、`暫停（<原因>）`。箭頭只接在已結案後面；暫停一定要寫原因。
- **第二欄**：已合併、已結案是結束，寫「完成：」；其他寫「下一步：」。等觸發點的觸發點寫在下一步。都不能空。
- **等誰**：使用者、Claude、Codex、實機、—；好幾個用「、」接，不重複；「—」只能單獨用。結束與等觸發點寫「—」。
- 經過寫在內文（例如〈結果〉〈進度〉），不寫在狀態行。

新寫的任務說明、討論稿與 plans 一律用這個格式；2026-11-21 以前的照舊（凍結清單在 `tools/legacy-status-docs.json`），改成新格式後就照新格式檢查。

## 連結

- **站**：任務說明、討論稿、plans，一份檔是一站；backlog 的一項是一站（檔＋最近的標題）；決定是決策紀錄裡的那一條。
- **來自**：新的一站在第一個二級標題之前寫一段 `來自：<連結>`；從好幾處合併來的用「、」接。決定寫在狀態行的「來自」段。
- **→ 下一站**：上一站加一行 `→ <連結>（YYYY-MM-DD）`，「→」後面直接接連結；backlog 寫在項目的下一行。拆成好幾站就寫好幾行。寫了不再改。
- 文件檢查擋：「→」的日期不是真的日期；「→」指到的站沒有「來自」連回這一站（從 backlog 出發的要連回同一個標題）；「→」指到 D-218 以前的決定；「來自」連到的一站沒有「→」連回來（連到決定的除外）。

## 只讀需要的那一段

- 讀長文件（backlog、roadmap、quality.md、決策紀錄）只取需要的那一段（D-215 第 6 點）：`node tools/section.ts <檔案> <標題>` 印那一節與行號；`node tools/section.ts <檔案>` 列出每個標題的行號與字數。
- 入口文件只讀上面那一節：backlog 的〈待處理〉、roadmap 的〈現在在哪裡〉。
- 決定用查詢工具讀，不整份讀決策紀錄。

## 狀態放在 repo

開發狀態留在 repo（D-215 第 1 點）。上線後若純狀態更新仍常造成衝突、等 push，或接手的 session 找不到最新的下一步，再用 3～5 件能由單一 PR 結案的新任務試行 GitHub Issues。
