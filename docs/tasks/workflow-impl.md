### 2. 入口的狀態行

標題下第一個非空行，一般段落（不在引用框、程式碼區塊裡）：

```text
狀態：<狀態值>｜下一步：<一句>｜等誰：<值>
狀態：已合併｜完成：<一句>｜等誰：—
```

文法（D-217 第 2 點；解析放在 `tools/status-line.ts`，文件檢查與產生狀態板的工具共用）：

- 一行剛好三欄，用全形「｜」分；欄裡不能再有「｜」（改用「，」）。欄名依序是「狀態：」「下一步：」或「完成：」「等誰：」，冒號是全形。
- 狀態值只收：規劃中、討論中、實作中、待審、待實機、等觸發點、已合併、已結案、`已結案 → <D-ID 或連結>`、`暫停（<原因>）`。箭頭只能接在已結案後面；暫停的原因不能空。
- 已合併、已結案（含箭頭）是結束：第二欄是「完成：」，等誰是「—」。其他狀態第二欄是「下一步：」；等觸發點的等誰是「—」，觸發點寫在下一步。第二欄的內容不能空。
- 等誰只收使用者、Claude、Codex、實機、—；可以用「、」接好幾個（例如「Claude、Codex」），不能重複，「—」只能單獨用。
- 經過寫在內文（例如〈結果〉、〈進度〉），不寫在狀態行。
- 正例：`狀態：暫停（等 0.7.0 發布）｜下一步：發布後接著做｜等誰：—`、`狀態：已結案 → [D-218](../decisions.md#…)｜完成：談定｜等誰：—`。反例：`狀態：已合併｜下一步：…`（結束要寫完成）、`狀態：做完了｜…`（不是狀態值）、`狀態：暫停｜…`（沒原因）、`…｜等誰：使用者、使用者`、`…｜等誰：—、Claude`、`狀態：實作中｜下一步：｜等誰：Claude`。

文件檢查（`check-docs.ts`）：

- **新寫的狀態檔一律新格式**：現有的任務、討論稿、plans（最上層與外掛的 `docs/tasks/`、`docs/Claude Codex Discussion/`、`docs/plans/` 第一層，README 除外）凍結成一份清單（`tools/legacy-status-docs.json`，上線時從 `git ls-files` 產生一次）；清單外的狀態檔，標題下第一行要能照上面的文法解析。清單裡的照舊（D-217 第 6 點）：原本的「標題下第一行要有狀態」與 D-195 的〈結果〉檢查不變，「狀態：已合併｜完成：…」仍算結束。清單裡的檔不在了，報「請刪掉這一列」。
- 任何追蹤的 Markdown，標題下第一行以「狀態：」開頭又含「｜下一步：」「｜完成：」「｜等誰：」其中之一，也照文法檢查（清單裡的舊檔改成新格式時就會被查）。
- 狀態板與〈等觸發點〉的入口（例如 card-rules）由〈5〉的工具查。

### 3. 「來自」與「→ 下一站」

- **站**：任務、討論稿、plans 與其他有「來自」的檔，一份檔是一站；backlog 的一站是「檔＋最近的標題錨點」（一份 backlog 有很多項目）；決定是 `decisions.md` 裡那一條的錨點。
- **來自**：新的一站在第一個二級標題之前寫一段 `來自：<連結>`，一份只有一段；從好幾處合併來的，連結用「、」接。新決定寫在狀態行的「來自 …」那一段。
- **→ 下一站**：上一站加一行 `→ <連結>（YYYY-MM-DD）`：段落或清單項目裡的一行，「→」後面直接接連結（現有文件裡「→」後面不是連結的行照舊，不算）；backlog 的項目寫在項目的下一行。拆成好幾站就寫好幾行。之後不再改。
- **文件檢查**：
  - 「→」那一行要有真的日期（`（2026-02-30）` 不算）。
  - 「→」指到的站要有「來自」連回這一站：指到檔，看那份檔的「來自」有沒有連到這份檔（從 backlog 出發的要連到同一個標題錨點）；指到決定，看那一條狀態行的「來自」。指到舊決定（分界之前）報錯：舊決定沒有「來自」。
  - 「來自」連到一站（決定以外的 Markdown 檔）時，那一站要有「→」連回來；連到決定的不用（決定的「現在在哪」由工具算，D-214 第 5 點不改舊決定）。
  - backlog〈待處理〉裡不能有「→」：轉出的項目搬到〈已轉出〉（D-214 第 4 點）。
- **往前的鏈由工具算**：「→」與反過來的「來自」都算一條邊；走到沒有新的邊為止，遇到走過的站（退回造成的循環）就停。走到的最下游可能不只一站（拆分），都列出來。

### 5. 狀態板、〈等觸發點〉與〈已完成〉由工具產生：`tools/roadmap-sync.ts`

使用者 2026-11-21 選 Q1 的 A：每份 roadmap 自己一套，列從哪一份來就留在那一份，工具不跨檔搬列。

- **狀態板**（〈現在在哪裡〉的表，欄照舊 `工作｜狀態｜下一步｜等誰｜入口`）：手寫的只有工作與入口，只在開工時加一列。入口一格剛好一個連到 Markdown 檔的連結，那份檔的狀態行要是新格式。工具把狀態、下一步、等誰寫進去。
- **〈等觸發點〉**（表：`工作｜觸發點｜入口`）：
  - 工具的列：入口一格剛好一個連結，連到標題下第一行以「狀態：」開頭的 Markdown 檔（決策紀錄除外），那一行一定要能解析，解析不了就報錯（不會被當成手寫）。狀態是等觸發點的列，工具從狀態板搬過來，觸發點取「下一步」；狀態改成別的進行中，工具搬回狀態板最後面。
  - 手寫的列：入口只有 D-ID、連到沒有狀態行的紀錄（例如 `card-rules/trials.md`），或沒有連結；工具不動。
- **〈已完成〉**（表：`日期｜工作`）：入口的狀態是已合併或已結案的列，工具從狀態板或〈等觸發點〉移到〈已完成〉表的最上面（同一次好幾列照原本的順序），寫成 `**<工作>**：<完成>（<已合併或已結案>，[入口](<路徑>)）`。
  - 日期是收尾的 commit：入口檔在工作樹或暫存區有沒 commit 的修改，就是今天（台北時間）；否則往回找入口的歷史，取狀態第一次變成結束的那個 commit 的日期（台北時間）。hook 擋在同一個 commit 搬列，所以通常就是今天；之後 rebase、squash 不回頭改。
  - 已有的列不動。暫存區新加的〈已完成〉列（暫存區有、HEAD 沒有）要是工具的格式、入口在暫存區已結束、「完成」那一句一致：手寫的完成列擋下。重開已結束的工作：照舊在開工時手寫一列。
- **連結改寫**：下一步、觸發點、完成三處都可能有連結，搬進 roadmap 時共用同一個改寫：相對路徑改成以 roadmap 為基準，只有錨點的（`#結果`）改成連到入口檔的那個錨點，有空白的路徑用 `<…>` 包起來；參照式連結（`[文字][名稱]`）報錯；格子裡的直線跳脫成 `\|`。工具寫出的 roadmap 要過得了文件檢查與白板（測試）。
- **同一個入口**在狀態板與〈等觸發點〉出現兩次報錯。
- **執行**：`node tools/roadmap-sync.ts` 改寫工作樹的 roadmap；`--check` 只比對、不寫，不一致就印「檔案:行號  原因」與「執行 node tools/roadmap-sync.ts，再 git add <roadmap>」並 exit 1；`--staged` 只能和 `--check` 一起用，roadmap、入口與 HEAD 的比較都讀暫存區，不混讀工作樹；`--root` 給測試。冪等：跑兩次第二次不改任何字。
- **接線**：`tools/hooks.ts` 的 `SHARED_CHECKS` 在 `roadmap-board` 之前加 `roadmap-sync.ts --check --staged`；`tools` 的 `npm run check` 加 `npm run roadmap-sync -- --check`（CI 的 shared job 跑這個）。

### 7. 決策查詢工具：`tools/decisions.ts`、`tools/decisions-index.ts`

- 搬進 `tools/`（有型別、lint、測試，沒有 npm 相依）；`experiments/tools/decisions-index.mjs` 留一行轉呼叫，舊文件與 AGENTS.md 寫的指令照樣能用。
- **新決定的寫法**（從分界編號起，D-214 第 10 點；暫定 D-218，合併前看 `origin/main` 的最大號加一，改 `BOUNDARY`）：

  ```markdown
  ## D-xxx 名稱

  ✅ YYYY-MM-DD｜來自 [plans/A](plans/A.md)｜修改 [D-yyy](#…)（第 n 點）、補充 [D-zzz](#…)｜取代 [D-www](#…)

  主題：<索引的主題之一>｜一句話：<一句>

  適用：全部
  ```

  - 狀態行用「｜」分段，順序不限、可以重複；「來自」「修改」「補充」「取代」開頭的段裡的 D-ID 是這條的上游，要是存在而且比自己小的，否則報錯。其他段（例如來源說明）不看。
  - 「主題：…｜一句話：…」一行，主題是索引既有的 8 個之一，一句話不能空。
- **索引由工具產生**（D-214 第 5 點）：分界之後的主題與一句話讀條目；之前的主題讀凍結的對照表（不再新增）、一句話照舊從現有索引保留。測試要求真的決策紀錄和工具產生的一模一樣（改了決定沒重產就擋）。第一次重產只有索引的說明句不同。
