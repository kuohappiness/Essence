# 試行：L2 的再審輪由 Claude 自己叫 Codex（給 Claude，本機執行）

狀態：已被取代（2026-11-20）→ [D-212](../decisions.md#d-212-claude-直接呼叫本機-codex任務開始時分本機或雲端)：Claude 直接呼叫本機 Codex 已是正式做法、第一輪也包含在內；這個試行沒有在第一步的 L2 用上，也不再另找一件試（Claude 2026-11-20 整理）

遵守 repo 根目錄的 `AGENTS.md`。建議模型與推理等級：**Opus、高**。這份由施工[第一步](one-repo-step-1.md)的那個本機 session 一起做，它就是那件 L2 的整合者。**這是試行，不是決定**：量完由使用者看結果決定要不要寫成 D-ID、改 `quality.md` 與 code-quality 的 `review.md`；試行期間只有下面寫的地方和現行規則不同。

## 為什麼要試

- **瓶頸是轉交，不是審查本身**：AI 製卡最小版的 L2 審了七輪，中間有三段整個 repo 沒有 commit，16.3、4.2、7.6 小時，共 28 小時；那時下一輪的請求已經寫好，只是等使用者貼給 Codex（2026-11-18「流程效能優化2」討論串，Claude 抽查屬實；一部分是睡覺時間，只有電腦開著才省得回來）。
- **以前為什麼沒做**：[D-106](../decisions.md#d-106-claude-與-codex-的協作流程) 把「Claude Code CLI 橋接」擱置，理由是缺少足以支持建置成本的證據、有明顯問題再談；[D-171](../decisions.md#d-171-省-token-靠縮短上下文不靠少審或換模型) 的討論稿 §3 不做，是因為它省時間、不省 token。現在要省的正是時間，等待的數字也有了。
- **建置成本很小**：`codex exec` 是 Codex CLI 內建的非互動執行，不用寫橋接程式；每次執行都是新的 session，正好符合 D-171 第 1 點的「每輪新開」。

## 和「不做」比較（D-153）

| | 不做（現行） | 試行 |
|---|---|---|
| 再審輪的等待 | 請求寫好到使用者貼給 Codex，幾分鐘到十幾小時，看使用者在不在 | 請求寫好就送，等 Codex 跑完（估計幾十分鐘） |
| 使用者要做的事 | 每輪開新對話、貼請求、把報告帶回 | 第一輪照舊；再審輪不用做，第四輪或要選擇時才出場 |
| 審查的獨立性 | 新開的 Codex，只讀請求點名的段落 | 同樣是新的 Codex session、同一份請求文字；Codex 在唯讀沙箱，改不了檔案 |
| token | 不變 | 大致不變（D-171 討論稿 §3）；`--json` 的用量順便記下來比 |
| 代價 | 每一輪最長等一個晚上 | 電腦與 Claude Code 要開著；使用者每輪少看一次報告，要等第四輪或結案才看到；沙箱裡跑不了的測試要另外處理（下面〈預檢〉） |

使用者少看幾次報告的代價：停止條件（下面第 4 節）把要使用者判斷的發現都擋下來交給使用者，結案時使用者照樣讀整份報告。

## 範圍

- **只試一件**：[第一步](one-repo-step-1.md)合併前的那件 L2。
- **第一輪照舊**：使用者新開 Codex 對話、貼請求，Codex 跑完整的檢查。第一輪是整份審查，又要在沙箱外跑完整的 `npm run check`（[`quality.md`](../agents/quality.md#檢查指令)〈檢查指令〉），先不動。
- **再審輪（第二輪起）由 Claude 自己用 `codex exec` 送**，到第四輪為止（D-171 第 3 點不變）。
- **再審輪只跑請求點名的測試**：同一個 commit 的 pre-commit 與 CI 已經跑過完整的檢查，請求的〈驗證方式〉寫這一輪要 Codex 跑哪幾個測試檔或指令，其餘列 CI 的 run 網址當證據。
- **不在範圍**：CI 不改（repo 公開，不扣額度）；送 Codex 之前先用 Claude 子代理預審，等這次量完再談；開工前的格式查核與討論稿的輪次照舊由使用者轉交。

## 1. 預檢（不用等 L2，越早做越好）

在使用者的 Windows 電腦、這個 repo 的工作樹裡，用一份自編的小請求（例如「讀 `tools/check-docs.ts` 的前 40 行，用一句話說它做什麼，再跑 `node --test tests/check-docs.test.ts` 回報結果」）逐項試，結果填進下面的〈平台事實〉。官方文件寫的：`codex exec` 不開互動畫面、沿用已登入的帳號、預設唯讀沙箱、`-o` 把最後的回覆寫成檔、`-m` 指定模型；推理等級的參數文件沒寫。

1. `codex --version`、`codex login status`：用的是使用者的 ChatGPT 訂閱登入，不是 API 金鑰。是金鑰就停下來問使用者（會另外計費）。
2. 請求從檔案用標準輸入送（`codex exec … - < 請求.md`），中文與換行不被 shell 弄壞；送不了再試把路徑寫在一行短提示裡、請 Codex 自己讀。
3. 推理等級：試 `-c model_reasoning_effort="high"`，再到 `%USERPROFILE%\.codex\sessions` 這次的 session 檔核對實際的等級與模型（只讀 `turn_context` 與 `token_count`，不讀對話內容）。模型和使用者平常開的一樣就不加 `-m`；不一樣才加。
4. 沙箱：預設的唯讀沙箱裡，`node --test` 單一測試檔能不能跑（測試會寫暫存資料夾）。不能跑就試 `-s workspace-write`，跑完 `git status` 要是乾淨的。兩種都不行時，那個測試由 Claude 在沙箱外自己跑、把輸出貼進請求，Codex 只讀；這種情況在報告標「Claude 代跑」。**不用 `--dangerously-bypass-approvals-and-sandbox` 或 `danger-full-access`**：Codex 只審查，不能有寫 repo 的權限（[D-131](../decisions.md#d-131-claude-實作codex-在關鍵點查核)）。
5. 報告：`-o <repo 外的檔>` 拿到最後的回覆；`--json` 的事件另存一份到 repo 外（`%TEMP%\essence-codex-exec\`），用來量時間與 token。兩份都不 commit。
6. 跑多久、會不會卡住：Claude Code 的指令放背景跑（前景最多 10 分鐘），設 60 分鐘上限；超過就停掉、當這一輪失敗。
7. 權限：Claude Code 叫 `codex exec` 要使用者核准；使用者睡覺時跳出核准會卡住，所以在**本機的** `.claude/settings.local.json`（不進 repo）加允許 `codex exec` 開頭的指令。先請使用者同意再加，試行結束後刪掉。

預檢有一項做不到，又沒有上面寫的替代做法，就停下來告訴使用者哪一項、錯誤訊息是什麼，L2 照現行規則由使用者轉交。

## 2. 每一輪再審怎麼送

1. 照現行規則修完、commit、push，等 CI 綠燈（pre-merge-commit 本來就要）。
2. 照 `quality.md`〈高風險範圍〉在 `tasks/one-repo-step-1-review.md` 寫這一輪的請求（開頭「這一輪只讀：……」、還沒結的發現 ID、延續的標法照 `review.md`），〈驗證方式〉列出點名的測試；請求本身 commit 並 push，記下時間（**請求時間**）。
3. 把這一輪的請求另存成 repo 外的檔，第一行照舊寫「新開一個 Codex 對話，推理等級：高」，加一句「這一輪由 Claude 用 `codex exec` 送：唯讀沙箱，不改任何檔案；報告寫在最後的回覆」。
4. 確認工作樹乾淨、HEAD 是待審的 commit，在工作樹的根目錄執行預檢定下的指令（`-C <工作樹>`、沙箱、推理等級、`--json`、`-o`）。
5. 跑完先看 `git status`：有任何變動就算失敗，還原前先把變動存到 repo 外、告訴使用者。
6. 把 `-o` 的報告原文貼進 L2 報告檔（`Claude Codex Discussion/` 裡這件的 `-l2.md`）那一輪的「第 N 輪」底下，標題後加「（`codex exec` 自動送）」，記下**報告時間**；之後照 `review.md`〈修正後收尾〉核對、寫〈Claude 回應〉，和使用者轉交的那一輪一樣。

## 3. 量什麼

每一輪記一列，寫進本檔的〈結果〉：

| 欄 | 怎麼量 |
|---|---|
| 輪次、送法 | 使用者轉交或 `codex exec` |
| 請求時間 → 開始審 | 請求 commit 的時間到 Codex session 第一個事件的時間；使用者轉交的那一輪從使用者的 session 檔讀 |
| 開始審 → 報告 | 同一個 session 的第一個到最後一個事件 |
| 報告 → Claude 回應 commit | 看整合者這端有沒有變成新的瓶頸 |
| Codex 的 token | 輸入、快取外輸入、輸出、推理等級（`token_count` 的 `last_token_usage` 加總） |
| 跑了哪些測試、有沒有「Claude 代跑」 | 報告的驗證段 |
| 品質 | 報告有沒有照範本（真實路徑、發生機率、延續的標法）；有沒有改到檔案；有沒有因為自動送而多出一輪 |

對照組：同一件的第一輪（使用者轉交），以及 AI 製卡最小版那三段空檔。

## 4. 停下來交給使用者

照現行規則會停的照停，加上這次才有的：

- 第四輪之後還有擋合併的發現（D-171 第 3 點）。
- 有發現照 [D-207](../decisions.md#d-207-l2-的發現先分一定修可記限制交使用者選修法先收窄最後才加機制) 歸成「交使用者選」，或修法會改到看得到的行為：這一項先不修，其他的照修，送下一輪前問使用者。
- `codex exec` 失敗（登入、額度、逾時、改到檔案）：這一輪改由使用者轉交，請求不用重寫。
- 結案或停下時，在這個任務的討論串（或使用者正在看的地方）一次報告：輪數、每輪的時間、還剩什麼。

## 5. 試完之後

- 〈結果〉寫上表的數字與一段結論：再審輪的「請求 → 報告」比使用者轉交短多少、品質有沒有變差、哪些地方卡住。
- 有用（再審輪的等待明顯變短、報告照範本、沒有改到檔案、沒有因此多一輪）：照 [D-140](../decisions.md#d-140-fable-規劃opus-執行codex-查核) 寫討論稿，請 Codex 站在「不做」那一方反駁（[D-177](../decisions.md#d-177-先問會不會明顯更好優勢明顯代價解決得了就該做)），雙方一致再交使用者決定要不要寫成 D-ID、改 `quality.md` 與兩份 `review.md`、第一輪要不要也自動。
- 沒用：〈結果〉寫卡在哪裡，backlog 記一列重新評估的條件。
- 不管結果，刪掉 `.claude/settings.local.json` 裡試行加的允許。

| 假設 | 探針與環境 | 結果 |
|---|---|---|

| 每次 `codex exec` 都是新的 session，看不到前幾輪 | 預檢時連跑兩次，第二次問第一次的內容 | 待驗 |
